# Design-feedback 스킬

동료(PO·개발자·PM 등)가 만든 프로토타입에 대한 디자인 피드백을 "레벨 판정 → 범위 내 리뷰 → 태그 피드백 → 슬랙 회신 초안" 순서로 처리한다.

**기준 SSOT**: `~/agent-workspace/docs/design-feedback-criteria.md`
Step 1 전에 반드시 Read. 파일이 없으면 `references/criteria-snapshot.md` 사용 (스냅샷일 뿐, 충돌 시 SSOT가 우선).

**판단 근거 SSOT**: 디자인 아틀라스 (`Ohouse-product-design/ohouse-design/knowledge/`). 세션에 ohouse-design MCP가 있으면 그걸로 로드(list/get_design_knowledge, get_screen), 없으면 gh api로 raw 파일을 읽는다. 레벨별 로드 범위는 Step 2 참조.

## Step 0 — 인풋 수집

받을 수 있는 인풋과 처리:

| 인풋 | 처리 |
|---|---|
| 슬랙 스레드/메시지 링크 | Slack MCP(slack_read_thread 등)로 요청 내용 읽기 |
| 자가추출 번들 HTML (AI 프로토타입 내보내기, 수십 MB급 단일 파일) | Read 불가. 에셋 번들(gzip 매니페스트)과 분리해 마크업·스크립트를 추출한 뒤 소스를 정독한다 |
| 요청 텍스트 (복붙) | 그대로 사용 |
| Figma URL | Step 2에서 get_screenshot + 필요 시 get_design_context |
| 화면 이미지 / 프로토타입 링크 | 이미지는 직접 분석, 링크는 접근 가능하면 열람 |

요청에서 **판정 3요소**를 추출한다: ① 누가 쓰나 (대상 사용자) ② 몇 명이 얼마나 자주 쓰나 (규모) ③ 오류·실수 시 피해 유형 (금액 오류 / 데이터 손상 / 잘못된 정보 고객 노출 / 없음 = 되돌리기 비용).

**+ 산출물 성격을 확인한다 (2026-07-23 추가, 기본값 규칙은 당일 확정)**: "이 화면의 용도는 무엇인가요?"
- **기본값 = 산출물형.** "실서비스로 이관되는가"를 따지지 않는다. **논의용 러프 프로토타입이라는 명시가 있을 때만 면제** (디어 확정: "프로토타입이 아닌 경우에는 이 규칙을 적용")
- **논의용** (구조 합의, 옵션 비교, 방향 논의 — 요청자가 명시한 경우만): 레벨 판정 + 기준 순회만. 가이드 전수 대조·기준 13·ODS 정합 생략 (안전선 1~4는 항상). lofi-wire 스킬 영역과 겹치면 그쪽 권장
- **산출물형** (그 외 전부): L2 이상 가이드 전수 대조 + 수정 프롬프트에 **ODS 정합 4종 패스 기본 포함** (색 면적·역할, 버튼 variant 위계, 타이포 웨이트, 스페이싱 4px 배수). "고객한테 나가도 되는가"의 판단에 ODS 정합이 포함되기 때문
빠진 항목은 요청문·화면에서 추론하되, 출력에 `(추론)` 마커를 붙인다. 셋 다 추론 불가면 사용자에게 그 항목만 짧게 확인.

요청자가 양식 없이 보낸 경우, 회신 초안 마지막에 다음부터 쓸 요청 양식(`references/request-template.md`)을 첨부할지 사용자에게 제안. (이 게이트는 요청자에게 보내는 메시지 톤 결정이라 Step 1의 fast-path 대상이 아님 — 항상 확인)

## Step 1 — 레벨 판정

SSOT 문서의 4축(노출, 규모, 되돌리기 비용, 수명)으로 레벨을 정하고, 대상 사용자 보정을 적용한다.

- 셀러/파트너: 트래픽 낮아도 돈(정산·광고비·수수료)·데이터 걸리면 한 레벨 승격
- 브랜드사: 사용 빈도보다 관계 리스크로 판정
- 어드민: 새 인터랙션 패턴의 선례가 되는 화면이면 레벨 승격

출력 포맷:

```
[레벨 판정]
레벨: L2 (흐름 + 표준)
근거: 노출=셀러 / 규모=일 n회 운영 툴 / 되돌리기=정산 데이터 직결 → 승격 / 수명=지속
대상 사용자 관점: 셀러 — 정보 정확성, 반복 작업 효율에 힘줌. 비주얼 폴리시는 안 봄
이번 리뷰에서 보는 것: …
안 보는 것: …
```

판정 후 사용자 컨펌을 받고 Step 2 진행. 사용자가 레벨을 조정하면 그 레벨로. 단 아래 **fast-path 조건을 모두 충족하면 컨펌 없이 선진행**하고, 회신 초안 첫머리에 판정 전제를 자연어로 명시한다 ("셀러 대상 산출물형 L2 기준으로 봤어요. 아니면 알려주세요"). 근거: 시뮬·실전 4회 연속 자동 진행에 사후 정정 0회 (2026-07-28 확정).

- 판정 3요소가 양식 답변 또는 명확한 추론으로 확보됨 (하나라도 추론 불가면 컨펌)
- L1/L2 경계가 애매하지 않음 (cases.md의 "경계 애매" 기준)
- L3 판정이 아님 (L3 전환은 항상 사용자 컨펌 — 디자이너 협업 투입 결정이라)

**돈/신뢰 판정 주의 (2026-07-23 콜드스타트에서 확인)**: L3 승격 대상은 **돈이 걸린 기능**(정산·결제·과금 트랜잭션이 실제로 도는 화면)이다. **돈을 언급하는 정보·마케팅 페이지**(비용·수수료 약속 문구 등)는 L2 유지가 기본이되, 기준 3(정보 신뢰)을 블로커 기준으로 엄격 적용한다.

**L3 판정 시**: 리뷰를 진행하지 않는다. "이건 리뷰 범위가 아니라 디자이너가 협업자로 들어가야 하는 건"이라고 안내하고, design-review 스킬 워크플로우(페르소나 → 유저보이스 → 리뷰 → 스펙 → 크리틱)로 전환할지 확인.

## Step 2 — 범위 내 리뷰 (판단 기준 12개로만 판단)

판정된 레벨의 범위만 본다. 레벨 밖 이슈가 보여도 본 리뷰에 섞지 않는다 (Step 3의 "범위 밖 메모" 한 줄로만).

**순회 인덱스는 SSOT §4의 판단 기준 12개, 판단 권위는 디자인 아틀라스.** 모든 지적은 아틀라스 출처를 인용해야 한다 (최대 2개). 인용할 출처가 없으면 취향이므로 [사소]로 강등하거나 뺀다.

| 레벨 | 순회하는 기준 | 아틀라스 로드 |
|---|---|---|
| L1 | 1~4 (안전선: 오해 방지, 비가역 보호, 정보 신뢰, 패턴 재사용) | 로드 없이 진행 가능 (인용은 SSOT §4 출처 컬럼) |
| L2 이상 | 1~9 (+ 과업 완결, 상태 완결, 일관성, 실수 방지·효율, 카피 명확성). AI 프로토타입이면 + 13 비주얼 베이스라인 (대상 사용자 무관) | **knowledge 전 문서 로드**: principles, feedback-format, ux-design, ux-writing, visual-design, **design-insight** (인용 원문·severity 가이드·인사이트 #13 엣지 조합·#14 의미 그룹핑 보유). clauses가 있는 문서(UXW-*, UXD-*)는 조항 단위로 화면과 대조 |
| L2 이상 + **논의용** | 기준 순회는 동일하되 조항 전수 대조·기준 13·ODS 생략 가능 | principles + feedback-format 2개로 축소 가능 (인용·severity용 최소 세트) |
| L3 전환·새 패턴 발명 검토 시 | Composition Order 판단 | + decision-framework (Design 모드 문서. Decision Spec 템플릿 포함) |

**전 문서 로드는 줄이지 않는다 (2026-07-23 디어 지시).** "관련 문서만 골라 로드"로 운영하다 ux-writing 위반 5건(용어집·표기 일관·과장 표현)과 ux-design 위반 2건(reduced-motion, CTA 대비)을 첫 리뷰에서 놓친 사례가 있다. 토큰 절약보다 커버리지가 우선. 로드는 ohouse-design MCP(list/get_design_knowledge)로, 로컬 클론 불필요.

**로드 증명 의무 (2026-08-05 디어 확정).** 리뷰 출력(커버리지 보고, Step 2.5)에 `로드한 knowledge: ...` 한 줄을 필수로 포함한다. 이 줄을 쓸 수 없으면 아직 리뷰를 시작하지 않은 것이다. "스킬을 기억한다"는 로드가 아니다 — 크로스셀 실전에서 로드 생략 상태로 리뷰를 진행해 라이팅 4건·에셋 근거를 통째로 놓친 사례 (2026-08-05, 인사이트 1 "읽어야 보인다"를 스스로 어긴 건). 기존 검증 결과 재사용은 **동일 지면·동일 파일**일 때만 허용하고, 그 경우에도 재사용 사실을 판정 출력에 명시한다.
| L3 | 1~12 — 단 L3는 design-review로 전환이 원칙 | design-review 워크플로우가 담당 |

**Screen 정책 확인 (고객단 화면, L2 이상)**: 크리틱 전 이 화면이 어느 Track Screen인지 식별하고 ohouse-design MCP get_screen으로 정책을 확인한다. Screen 정책이 최우선 인용 권위. 화면 식별이 안 되면 첫 질문은 "이 화면이 어디인가요?".

**시작 5질문 (L2 이상, feedback-format §1-1)**: 문제→솔루션 적합성 / 변수 통제 / 디폴트값 / 화면 1순위 / 일관성. 흐릿한 1~2개는 지적이 아니라 질문으로 되돌려준다.

**검증 주의사항 (2026-07-23 실전에서 확인된 함정)**
- **인터랙티브 프로토타입은 정적 캡처만으로 상태·연결을 판정하지 않는다.** 아코디언·토글·앵커는 접힌 상태 캡처에서 "없음"으로 오판된다. HTML 프로토타입이면 소스(스크립트의 state 포함)를 열어 실제 콘텐츠·연결을 확인한 뒤에 상태 누락을 지적한다.
- **번들 HTML은 인라인 마크업 밖 껍데기도 검수한다.** export 로더의 썸네일 스플래시(파일 미리보기·로딩 중 노출), 파비콘, 문서 title 같은 요소는 본문 치환 패스가 놓친다. 브랜딩·토큰 수정 시 껍데기까지 함께 (실사례: 구버전 색 썸네일이 수정본에 그대로 남아 파일 열 때마다 노출). **로딩 스플래시는 실제 레이아웃과 일치하는 스켈레톤으로 교체가 기본** (2026-07-23 디어 확정). 번들 압축 해제 0.3~2초 구간은 아틀라스 로딩 규칙상 정확히 스켈레톤의 시간대다 (원칙 6, 상태 표현 5종). 로고 카드 스플래시(로딩 존재감 과다)도, 순백 투명화(빈 화면 깜빡)도 아닌 **첫 화면 구조의 스켈레톤 + pulse 1.5s + reduced-motion 존중**. 스플래시 자체는 번들 포맷 부산물이라 실배포에선 불필요
- **번들 재조립 시 `</` 이스케이프 필수.** 인라인 마크업(JSON 문자열)을 수정해 되넣을 때 `</`(특히 `</script>`)를 이스케이프 없이 그대로 두면 로더가 "Error unpacking"으로 전체가 깨진다. `json.dumps(...) 후 .replace('</', '<\\u002F')` 라운드트립을 쓰고, 재조립 직후 렌더 스크린샷으로 언패킹 성공을 확인한 뒤 다음 수정으로 넘어간다 (실사례: 3차 시뮬 첫 조립본이 이걸로 깨짐, 2026-07-23).
- **헤드리스 Chrome은 창 폭을 최소 ~500px로 클램프한다.** `--window-size=390`으로 찍으면 500px 렌더가 390px로 잘려 "모바일 잘림"처럼 보이는 가짜 이슈가 생긴다. 모바일 확인은 반드시 iframe 기법 사용: 폭 390px iframe에 대상 페이지를 넣은 래퍼 HTML을 만들어 창폭 800으로 캡처.
- **스크롤 트리거 요소는 최소 3지점(최상단·중간·하단)에서 확인한다 (2026-08-05).** 한 지점만 보면 조건부 노출 요소를 놓친다 (실사례: 하단 고정 CTA를 '없음'으로 오판 — 확인한 최상단이 설계상 유일하게 숨겨지는 구간이었음). 코드 리뷰 시 `IntersectionObserver`·스크롤 리스너를 먼저 grep해 조건부 노출 요소를 목록화한 뒤 화면을 본다. 빈 fixed 컨테이너(높이 0, 자식 0)는 "없음"이 아니라 조건부 마운트 자리라는 신호다.
- **데이터 지면의 날짜는 적재일과 데이터 기준일을 구분해 판단한다 (2026-08-05).** 데이터 파이프라인은 D-1 적재가 관행이라 "작업일 07-23, 데이터 마지막 날짜 07-22"의 어긋남은 정상이다. 어긋남을 오표기로 단정하지 말 것 (실사례: OKR 대시보드에서 "하루 어긋남" 지적이 오판 — 제작자 DA가 관행 설명). 진짜 확인 포인트는 "그 날짜가 적재일인지 데이터 기준일인지 화면에서 구분되는가"다.

## Step 2.5 — 커버리지 보고 (필수, 2026-08-05 디어 확정)

```
[커버리지 보고]
로드한 knowledge: principles, ux-design, ux-writing, visual-design, design-insight (+feedback-format)
| 기준 (1~13 + 접근성) | 확인 방법 | 결과 |
| 1 오해 방지 | 카피 전수 | 발견 1건 |
```

- 이 표가 없으면 Step 3으로 넘어가지 않는다

## Step 3 — 태그 피드백 출력

모든 항목에 태그 + 아틀라스 출처(최대 2개)를 단다. 태그 순서대로 정렬 (블로커 먼저). 크리틱 작법은 feedback-format을 따른다: 결론 먼저, 우려 최대 4개, 40줄 미만, 체크리스트 줄줄 나열 금지. **단 우려 4개 상한은 [제안] 이하에 적용하고, 자동 블로커(안전선·접근성·토큰)는 상한 예외로 전부 보고한다.** **수정 프롬프트(Step 4.5)를 함께 제공하는 리뷰는 [제안]도 상한 없이 개별 나열한다 (2026-08-05 디어 확정)**: 상한의 목적은 요청자가 직접 고칠 때의 부담 관리인데, 자동 수정 경로가 있으면 각 항목이 체크리스트로 흡수되므로 묶어 압축하면 오히려 항목별 판단이 어려워진다.

```
[피드백 — L2 / 셀러 관점]
요약: {전반 인상 + 결론 한 문장}

[블로커] {위치}: {문제} (근거: 원칙 5 에러·빈 상태). 제안: {대안}
[제안] {위치}: {문제} (근거: design-insight #8). 제안: {대안}
[사소] {위치}: {참고. 주관 의견이면 명시}

질문 (0~3개): {yes/no로 답 가능한 확인 질문}
범위 밖 메모 (선택): {L3급 이슈가 보였다면 한 줄만. 없으면 생략}
산출물 전환 시 필수 (논의용 판정일 때만): {발행 전제가 아니라 이번 판정에서 제외한 항목 요약. 파일 내 TODO 마커는 개수·종류로 압축}
```

- 태그 = 아틀라스 severity 매핑: [블로커] = 🔴 차단 / [제안] = 🟡 강한 지적 / [사소] = 🟢 가벼운 제안
- [블로커] = 반영 안 하면 내보내면 안 됨. **기준 1~4(안전선) 위반, 접근성(WCAG AA)·디자인 토큰 위반은 자동 블로커**
- **접근성 자동 블로커의 사내 분기 (2026-08-05 디어 확정, OKR 대시보드 실전에서 도출)**:
  - **전 직원 열람형** (대시보드·리포트 등 사용자를 특정할 수 없는 사내 화면): **P0 유지**. 근거: ① 사용자를 특정할 수 없는 규모면 접근성이 필요한 구성원(저시력·색각 차이·키보드 사용자)이 존재한다고 가정해야 한다 — 고객이 아니라 동료라는 이유로 제외하면 특정 동료를 배제하는 결정이 된다 ② 대시보드는 "숫자를 읽는 것"이 유일한 과업이라 대비 미달은 접근성 항목이 아니라 기능 결함이다 (프로젝터·야외 사용 등 실환경에서 비장애 구성원도 못 읽음) ③ 수정 비용이 비대칭적으로 낮다 (토큰 값 몇 개 수준)
  - **소수 담당자 도구** (스쿼드 단위 공유 등 사용자를 이름으로 셀 수 있는 규모): 접근성 위반은 **P0 → P1 조정 가능**. 지금 사용자 중 해당자가 없음을 실제로 알 수 있는 경우에 한한다. 단서: 사내 도구는 수명이 길고 사용자가 늘어나는 경향이 있으므로 조정 시 그 사실을 기록한다
  - **선례 예외**: 새 패턴의 선례가 되는 화면(다른 화면이 복제할 본보기)은 사용자 수와 무관하게 **예외 없이 P0** — 선례가 복제되면 부채도 복제된다 (어드민 승격 규칙과 동일 논리)
  - 정보 신뢰(기준 3)는 사내 분기 대상이 아니다 — 의사결정 도구 특성상 사내가 오히려 더 엄격하다
  - 어느 분기든 비전공 요청자에게는 "왜 + 수정 비용이 낮다는 안내 + 수정 경로(수정본·프롬프트)"를 세트로 전달한다 (Step 4 요청자 눈높이 규칙과 연동 — P0 반발은 대부분 기준이 아니라 무게감의 문제)
- [제안] = 반영 권장, 판단은 요청자. 기준 5~9 위반은 기본 [제안], 유저 피해가 크면 [블로커]로 승격
- [사소] = 참고만. 출처 인용 없는 코멘트는 여기까지만 허용
- 블로커가 0건이면 "블로커 없음, 내보내도 됨"을 명시 (요청자가 가장 알고 싶은 것)
- **논의용 판정에서는 기존 TODO·예시 데이터를 블로커로 재보고하지 않는다 (2026-07-28 5차 시뮬 확정)**: 반복하면 노이즈, 묵살하면 "블로커 없음 = 발행 OK"로 오독될 위험. "산출물 전환 시 필수" 블록으로 분리해 한 번만 요약하고, "내보내도 됨"의 의미는 "이 구조로 논의 진행 OK"로 한정한다
- 우려끼리 충돌하면 원칙 우선순위 적용: 접근성 > 가독성 > 일관성 > 결정 피로

## Step 4 — 슬랙 회신 초안

사용자가 원하면 회신 초안을 작성한다. 반드시 `~/.claude/memory/work/feedback/feedback_slack-message-tone.md`의 규칙과 디어 말투를 적용:

**본문 구조 (2026-07-23 디어 확정)**:
- **카테고리는 고정하지 않고 그 건의 피드백 내용에 맞게 분류**해서 `[대괄호]` 섹션으로 묶는다. 예: `[사용성]` `[디자인]` `[데이터 신뢰]` `[케이스 고려]` `[확장성]` `[정책 확인]`. 억지로 채우지 않는다 (해당 피드백 없으면 그 카테고리 생략).
- **불렛마다 우선순위를 붙인다.** Step 1~3 판정에서 도출: [블로커]=P0(발행·머지 불가), [제안] 중 유저 피해·회귀 근거가 강한 것=P1(중요), 일반 [제안]=P2(권장), [사소]=P3(백로그·참고). 첫 등장에만 한글 설명 병기.
- **P1/P2 분기 기준 (2026-08-05 디어 확정)**: P1은 두 가지 — ① **전환·신뢰의 길목**에 있는 것 (첫 화면의 목적 전달, 과업 진입점 가시성, 신청 직전 망설임 해소) ② **리드타임이 긴 결정** (이미지 재제작처럼 늦게 결정할수록 비용이 커지는 것 — 영향도가 같아도 먼저 꺼낸다). P2는 마찰이지 차단이 아닌 것 (읽는 순서, 정돈, 표기).
- **성격이 다른 항목을 한 불릿에 묶지 않는다 (2026-08-05)**: 특히 신뢰 리스크(조건 없는 "보장"·단정 약속 — 기준 3의 연장, 최소 P1)는 표기·문체 항목(P2)과 묶지 않는다. 묶으면 가장 무거운 항목이 가장 낮은 등급에 묻힌다 (실사례: 절대 표현 5건이 P2 라이팅 묶음에 들어가 신뢰 리스크가 표기 문제로 강등됨).
- **우선순위는 백틱 인라인 코드로 감싼다** (`` `P0` `` 형태). 슬랙에서 회색 배경 칩으로 렌더링돼 뱃지처럼 보인다.
- 카테고리 안에서 P0 먼저 정렬. P0이 있으면 요약 줄에서 "제일 중요한 건 ~"으로 먼저 짚는다.
- **한 불렛 = 피드백 하나.** 여러 지적을 한 불렛에 섞지 않는다.
- **[반영 안내] 섹션을 마지막에 포함한다 (2026-07-23 디어 확정)**: 피드백을 반영하면 무엇이 얼마나 바뀌는지 요청자가 가늠할 수 있게.
  - 변경 규모: 특히 산출물형에서 토큰 전면 교체·색 인상 변화처럼 체감 변화가 큰 항목을 미리 알린다 (예: "색이 전부 현행 브랜드 블루로 바뀌어서 인상이 꽤 달라져요")
  - 자동/수동 구분: 에이전트 수정 프롬프트로 자동 처리되는 부분과 요청자가 직접 채울 부분(실데이터·정책 문구 등)을 나눠서 안내. 부담 완화가 목적
  - 가능하면 수정 적용본 파일을 함께 첨부 제안 (디어가 이미 반영해본 경우)
  - **수정 적용본 격상 분기 (2026-08-05)**: 브라우저 스타일 덮어쓰기 시안(CDP 오버라이드 등)은 "방향 공유용"으로만 표기한다. 고객 노출 지면의 실제 반영용 결과물은 원본 코드 수정(소스 접근 요청) 또는 시안 도구 재작업으로 격상하고, 공유 전에 그 결과물 자체를 기준 13으로 1회 재검수한다 (덮어쓰기 시안이 원본 타이포 스케일을 깨뜨린 실사례)

- 첫 줄 감사 + 시그니처 emoji (`:cat_pray:` 등), 긍정 평가 한 줄 먼저 ("전체 흐름은 좋아요")
- 마커 라벨은 직관적 한국어: `[이것만 고치면 돼요]` `[제안]` `[참고]`
- 질문·요청마다 부담 완충 ("판단은 편하신 대로!", "없으면 패스!")
- 레벨·범위 선언을 자연어로 한 줄 ("어드민 화면이라 안전선 위주로 봤어요")
- 긴 줄표 사용 금지, 범용 유니코드 이모지 금지

**전송은 초안까지만.** 사용자 확인 후에만 Slack MCP로 전송한다.

## Step 4.5 — 에이전트 수정 프롬프트 (옵션)

요청자가 바이브코딩 도구로 직접 수정할 수 있게, 피드백을 실행 가능한 프롬프트로 번역해서 슬랙 회신에 첨부 제안한다.

**논의용 + 블로커 0이면 수정 체크리스트 대신 "구조 옵션 비교용 프롬프트"로 대체한다 (2026-07-28 5차 시뮬 확정)**: 고칠 게 아니라 결정할 게 남은 상태라 수정 체크리스트가 빈 껍데기가 된다. 질문으로 남긴 구조 선택지를 옵션 A/B 별도 파일로 생성하게 하고, 스코프 가드·사람 입력 분리·완료 기준 규칙은 동일 적용. 비교 시안이 와이어 수준이면 lofi-wire 스킬로 넘긴다. (블로커가 있으면 논의용이어도 수정 체크리스트 유지)

규칙:
- **프롬프트는 1개**, 내부는 우선순위(P0→P3) 순 체크리스트
- 에이전트 작업 지시: "위에서부터 한 항목씩 수정, 항목마다 결과 확인 후 다음 진행" (한 번에 갈아엎기 방지)
- **스코프 가드 필수**: "체크리스트에 없는 것(레이아웃 구조, 섹션 순서, 카피)은 바꾸지 마"
- **사람 입력 필요 항목은 에이전트가 값을 지어내지 못하게 분리**: 실데이터·색값·정책 답변은 기존 값 유지 + `TODO:` 주석 처리 지시. 프롬프트 말미에 "요청자가 채울 것" 목록으로 명시
- 항목마다 완료 기준(검증 가능한 상태)을 한 줄로: "390px에서 가로 스크롤 없음"처럼
- P3는 체크리스트 말미에 "여유 있으면" 섹션으로 (백로그 성격 유지)
- **ODS 치환**: 산출물형이면 기본 포함, 논의용이면 생략. ods-prototype MCP(get_tokens, get_component, get_starter_files) 사용. 단일 HTML은 `:root`에 ODS 시맨틱 토큰 변수를 선언하고 하드코드 hex를 전부 `var(--ods-*)`로 교체 (잔여 hex 0이 완료 기준). React 프로토타입은 스타터 파일 기반으로 실제 컴포넌트 치환
- **치환은 값 교체가 아니라 사용처 정리까지 (2026-07-23 확정)**: 색값만 1:1로 바꾸면 원본의 색 남용·플랫한 버튼 위계가 그대로 남는다. 치환과 함께 반드시 **면적 기준 색 정리**를 동반한다 (2026-07-23 디어 확정, 과교정 주의):
  - **넓은 면적은 중립이 기본, 역할 있는 곳만 brandWeak**: 섹션·카드 배경은 white/gray 교차가 기본. brandWeak 배경은 **역할이 명확한 페이지당 2곳 내외만** — ① KV·히어로 (브랜드 진입 무드) ② 핵심 설득 모듈 (통계·증거 카드처럼 그 페이지가 제일 팔고 싶은 정보). 판단 질문: "이 배경색으로 무엇을 강조하려는가"에 답할 수 있으면 brandWeak, 못 하면 중립. 대형 텍스트(통계 숫자·제목)는 foreground 블랙. 버튼은 동시 노출 CTA 1개만 brand-solid, 나머지는 weak·text 변형 (`@ods: BoxButton {size} {variant}` 매핑 주석 필수)
  - **좁은 면적은 브랜드 리듬 유지**: 아이브로우 라벨, 단계·Q 칩, 도트, 점선 보더 같은 소형 액센트는 brandWeak/foreground-brand로 남긴다. **여기까지 걷어내면 플랫·와이어프레임화된다** (실사례: 전부 그레이 처리 → 디어 반려)
  - "가장 가까운 색값" 매핑 금지: 원본의 색 남용이 토큰 이름만 달고 살아남는다. 프라이머리는 위계 최상위에만
  - **스페이싱은 아틀라스 8pt 규칙으로**: ODS 패키지에는 spacing·radius 토큰이 없다 (컴포넌트 단위 내장 — get_tokens 명세 참조). 산출물형은 visual-design의 8pt 스케일에 따라 padding·margin·gap·border-radius를 4px 배수로 정규화한다 (1~2px 헤어라인은 제외). AI 산출물의 홀수 스페이싱(7px, 11px, 13px 등) 자체가 그리드 이탈 신호
  - **에셋(로고·아이콘·일러스트·플레이스홀더)도 실물 치환 (2026-07-23 추가)**: AI 산출물의 가짜 심볼("오" 박스, 빗금 해치 등)을 그대로 두지 않는다. ods-prototype MCP의 search_asset/search_icon으로 공식 에셋을 찾고 (예: AssetOhouseHorizontal, AssetPlaceholderOhouseSymbol), 단독 HTML에는 `asset.ohousecdn.com/static/{AssetName}/{kebab-name}.svg` CDN의 SVG를 받아 인라인 + `@ods:` 주석. 공식 에셋이 없으면 임의 제작 금지, TODO 주석. **주의**: 인라인 스타일 data URI는 percent-encoding(`data:image/svg+xml,%3C...`)으로 — base64의 `;`가 프레임워크류의 스타일 파싱에서 선언을 끊는 사례 있음. CDN 경로가 404면 파일명 조합을 바꿔가며 추측하지 않는다 — search_asset 결과에 있는 실제 경로만 신뢰하고, 확보 불가 시 텍스트 폴백 유지 + TODO 주석 (실사례: 로고 CDN 404, 3차 시뮬 2026-07-23). search_asset에 경로가 없으면 로컬 `@bucketplace/assets` 패키지의 URL 정의 청크(chunk-*.js)를 grep해 실경로를 확보할 수 있다 (2026-07-24 로고·파비콘 확보 사례)
  - **에셋 매핑 규칙 (2026-07-28 확정, 07-30 5차 시뮬로 보강)**: 의미 매칭은 LLM 추측 구간이라 아래로 통제한다. **매핑의 실체는 이름·태그 문자열 매칭이 전부다** — 검색은 의미를 이해하지 않고, 태그는 이름을 단어로 쪼갠 것(`IconArrowRight` → `arrow`·`right`)이다. 즉 "그 개념을 명명자가 어떤 영어 단어로 적었을까"를 맞히는 작업이며, 자동화되는 구간은 후보 검색 한 단계뿐이다 (루브릭에서 이 항목을 "반자동"으로 분류한 근거).
    1. **리소스 성격 판정 먼저**: 슬롯이 GUI 보조(버튼·라벨 옆 보조 심볼, ~32px, 단색 currentColor로 충분, 없으면 정보 전달이 깨지는 자리)면 `search_icon`(@bucketplace/icons 약 490종). 무드·설득·브랜드 존재감(히어로 KV, 빈 상태 일러스트, 프로모션 비주얼, 40px+ 단독 블록, 다색 고유 팔레트)이면 `search_asset`(@bucketplace/assets 약 820종 — 네이밍 분류: Photographic=실사, Art=일러스트, Motion=로티, Symbol·Horizontal=BI·로고). 정보성 모듈 자리엔 그래픽 에셋 금지(배너 톤은 광고로 인지 — design-insight E4 시스템 UI 톤), 애매하면 icon·텍스트 쪽으로(원칙 1 콘텐츠 조연). 에셋은 임의 recolor 금지, 아이콘은 토큰 색(currentColor) 상속
    2. **검색어는 한 단어, 구분자 금지 → 그 다음 동의어**: 검색이 이름·태그 부분일치라서 **공백·하이픈이 들어가면 무조건 0건**이다 (실측 2026-07-30: `arrow right` 0건 / `arrow-down` 0건 — 도구 설명의 예시인데도 0건 / `arrowright` 4건 / `arrow` 12건). 두 단어로 0건이 나오면 미보유가 아니라 **검색어 형식 문제**이므로, 한 단어 → 붙여쓰기 순으로 좁힌다. 형식을 맞춘 뒤에도 없으면 영어 동의어 2~3개로 재검색한 후에만 "없음" 판정 (실측 2026-07-28: 상담사 → "cs" 0건 / "headset" 1건 IconHeadset. "chart"·"graph"는 형식·동의어 모두 통과해도 0건 → 차트·그래프는 에셋 치환 대상이 아니라 직접 그린다)
    3. **치환 실행 전 매핑 표 컨펌**: 원본 요소 → 후보 에셋 → 선정 근거 표를 먼저 제시하고 사용자 확정 후 적용. 이름과 실제 렌더가 다를 수 있어 사람 확인 한 번으로 추측 리스크를 정리한다. 이 게이트는 fast-path 예외 대상이 아니다 (규칙 자체가 추측 통제 장치이므로)
    4. **슬롯 개수는 주석·산문을 걸러낸 뒤 센다 (2026-07-30 추가)**: 텍스트 기호를 아이콘으로 올릴 때 단순 문자 카운트로 슬롯 수를 세면 안 된다. 실측: 랜딩의 `→` 12곳 중 실제 아이콘 자리는 CTA 링크 1곳뿐이고 10곳은 HTML 주석, 1곳은 문장 속 화살표("상세페이지→구매 전환")였다. 전체 치환하면 11곳이 오염된다. 매핑 표에 개수를 쓸 때 주석 내부·산문 용법을 제외한 실슬롯만 센다
    5. **검색 결과에는 그림이 없다 → 실물 렌더로 확인 (2026-07-30 추가)**: `search_icon`/`search_asset`은 이름·import 구문·태그만 반환하고 **미리보기 이미지를 주지 않는다**. 따라서 `IconMagnifyingGlass`가 실제로 돋보기 모양인지 검색만으로는 확인할 수 없고, 이름과 실물이 어긋나 있어도 알 방법이 없다 (규칙 3이 존재하는 근본 이유). 모양 확인이 필요하면 로컬 `@bucketplace/icons` 패키지에서 뽑는다: `dist/{IconName}-*.js`가 `chunk-*.js`를 재export하므로 그 청크에서 `d:"..."` path와 `viewBox`·`fillRule`을 추출해 렌더한다. 에셋(이미지)도 동일하게 미리보기가 없으므로 CDN SVG나 로컬 패키지로 확인한다
    6. **아이콘 웨이트는 반드시 명시 (2026-07-30 추가)**: 아이콘 하나에 regular·medium·semibold·bold 4종이 들어 있고, **웨이트를 지정하지 않으면 렌더 결과가 비어버린다** (청크의 weight 분기 기본값이 빈 컴포넌트로 떨어짐 — 실측 확인). 소형 UI 아이콘은 regular를 기본으로 쓰고, 단독 HTML에 인라인할 때는 해당 웨이트의 path를 골라 넣는다 (청크 안 `{"monochrome|regular":X,...}` 매핑으로 변수 식별)
    7. **번들 HTML 치환은 이스케이프 형태를 먼저 확인 (2026-07-30 추가)**: 자가추출 번들의 템플릿은 JSON 문자열이라 속성 따옴표가 `\"`, 닫는 태그가 `</`다. 앵커와 **삽입할 마크업 양쪽 모두** 이 형태로 맞춰야 한다. 평문 `</span>`으로 앵커를 잡으면 0건 매칭으로 조용히 실패한다 (실측: 첫 시도 3건 전부 0건). 치환 후 렌더 스크린샷으로 언패킹까지 확인
  - **타이포 웨이트도 ODS 스케일로 (2026-07-23 디어 확정)**: ODS fontWeights는 400/500/600/700 네 단계뿐, **800은 시스템 밖** (AI 산출물의 800 남발은 그 자체로 토큰 이탈). bold(700)는 정말 강조(섹션 제목, 통계 숫자, CTA 라벨, 가격·할인율)만, 보통 강조 위계(뱃지·칩·라벨, 카드·단계 타이틀, FAQ 질문, 인용문, 본문 인라인 b)는 semibold(600), 본문은 400~500

## Step 5 — 사례 기록 (경계 보정용)

리뷰 완료 후 `~/agent-workspace/docs/design-feedback-cases.md`에 한 줄 append:

```
| 날짜 | 화면 | 대상 사용자 | 판정 레벨 | 블로커 수 | 경계 애매 여부 + 메모 |
```

사례 3~5건 쌓이면 L1/L2 경계 보정을 사용자에게 제안. 파일 없으면 헤더와 함께 생성.

메모에는 **오판 수와 누락 수를 함께 기록한다 (2026-08-05)**: 오판 = 잘못 지적한 것, 누락 = 사용자가 잡아준 발견. 누락이 반복되는 축(대비, 조건부 노출 등)은 Step 2.5 커버리지 표의 점검 항목으로 승격한다.
