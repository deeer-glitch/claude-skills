# Figma Frame Scaffold

이미 쓰고 있는 Figma 배치 체계로 화면을 만드는 스킬. 세 단계를 다룬다.

| 단계 | 하는 일 | 기본값 |
|---|---|---|
| 1. 골격 | 섹션, 라벨, 그룹 바, 케이스 바, 빈 프레임 | **내부는 비워둔다** |
| 2. 작화 | 기존 화면 컴포넌트를 가져와 채운다 | 사용자가 채우라고 할 때만 |
| 3. 주석 | 캔버스에 텍스트 레이어로 핸드오프 스펙 | 화면이 확정된 뒤에만 |

**요청이 없으면 1단계에서 멈춘다.** 골격만 잡아 달라고 했는데 내용을 채우지 않는다.

### 이 스킬이 아닌 것

- **Figma 코멘트 핀에 붙여넣을 텍스트 초안** 은 `spec-policy-handoff` (팀 공용). 애니메이션 파라미터와 lokalize key까지 다루는 더 깊은 포맷이다
- **로컬 HTML 와이어** 는 `lofi-wire`

## 이 스킬이 하는 일과 안 하는 일

| 한다 | 안 한다 |
|---|---|
| 섹션, 대주제 라벨, 그룹 바, 케이스 바 생성 | **컴포넌트 신규 제작** |
| 375x812 프레임을 이름 붙여 배치 | **기존 컴포넌트를 흉내낸 손그림** |
| 기존 화면의 컴포넌트를 가져와 화면 채우기 | 참고 파일 수정 |
| 캔버스에 핸드오프 주석과 리더 라인 배치 | Figma 코멘트 핀 작성 |

**채우는 것과 만드는 것은 다르다.** 이 스킬은 이미 있는 컴포넌트를 가져와 조립한다. 없는 것을 새로 그리지 않는다.

## 안전 규칙 (어기면 안 됨)

1. **참고 파일은 읽기 전용.** `use_figma`를 참고 파일에 쓸 때는 조회와 `return`만. 생성과 수정과 삭제 코드를 절대 넣지 않는다.
2. **골격 단계에서는 프레임 내부를 채우지 않는다.** 헤더, 텍스트, 버튼 스켈레톤 전부 금지. 빈 흰 프레임만 남긴다. 사용자가 채우라고 하면 2단계로 넘어간다.
3. **원본 컴포넌트 스타일을 임의로 바꾸지 않는다.** 폰트 크기, 색, 패딩을 손대지 않는다. 폭 조절과 텍스트 교체까지만.
4. **대상 파일과 페이지를 먼저 확인받는다.** 파일 키와 노드 ID를 사용자에게 받아서 쓴다. 추측하지 않는다.
5. **스타일은 실측한다. 추측으로 채우지 않는다.** 노드당 `fills`, `strokes`, `strokeWeight`, `strokeAlign`, `dashPattern`, `cornerRadius`, `opacity`, `effects`, 텍스트 `fills`/`fontName`/`fontSize`를 **한 번에 다 읽는다.** 일부만 읽고 나머지를 상속이나 감으로 두면 조용히 틀린다. 값이 없어 정할 수 없으면 지어내지 말고 물어본다.
6. 작업 후 **`get_screenshot`으로 검증**하고, **적용값을 다시 읽어 참고 파일과 대조한다.** 스크린샷만으로는 stroke 1px이나 불투명도 차이가 안 보인다.
7. **텍스트는 등록된 텍스트 스타일로 물린다.** `fontSize`와 `fontName`을 직접 찍어서 만들지 않는다. 아래 "텍스트 스타일" 절을 따른다.
8. **PRD는 정책과 요구사항만 SSOT다. 컴포넌트 제약으로 요구사항을 바꾸지 않는다.** 색, 위치, 닫기 위치, 컴포넌트 선택, 문구 같은 UI 디테일은 PRD 문장이 아니라 ODS 가이드와 사용성으로 판단하고, PRD와 다르다는 이유로 확인을 올리지 않는다(디어 2026-09-30). 요구사항 쪽에서 ODS 컴포넌트에 없거나, 지원 플랫폼 표기가 스펙과 어긋나거나, 라이브러리 제약 때문에 스펙대로 못 그리는 상황이 나오면 **그 자리에서 대안을 골라 그리지 말고 사용자에게 올려 결정받는다.** 컴포넌트 설명 문구 하나만 보고 판단하지 말고 코드 패키지도 함께 확인한다. Figma 라이브러리 표기와 코드 패키지가 다른 경우가 있다.
9. **UI를 창조하지 않는다. 기존 화면 컴포넌트를 갖다 쓴다.** 프레임 안을 채울 때 `createFrame` 과 `createText` 로 카드나 버튼을 조립하고 있다면 그 순간 잘못 가고 있다. 아래 "컴포넌트부터 찾는다" 절을 따른다.
10. **채우기 직전에 스펙 요약을 다시 읽는다.** 요약을 만든 것과 그대로 그리는 것은 별개다. 아래 "작화 전에 스펙을 다시 대조한다" 절을 따른다.
11. **이번 개편으로 달라지는 화면만 그린다.** 기존 서비스 개선 과업에서 Empty, Error, 스켈레톤을 새로 그리지 않는다. 아래 "그릴 화면을 정할 때" 절을 따른다.
12. **확정된 스펙만 그린다.** 미확정 항목은 화면으로 만들지 않고 확인 항목 문서에만 남긴다. 아래 "확정된 스펙만 그린다" 절을 따른다.
13. **인스턴스 폭을 바꿨으면 내부를 다시 실측한다.** 폭만 바꾸면 자식이 원래 폭에 고정된 채 남는다. 아래 "인스턴스 폭을 바꿀 때" 절을 따른다.
14. **"없다"고 말하려면 파일 전 페이지를 훑은 뒤에 말한다.** 작업 중인 섹션만 보고 단정하지 않는다. 아래 "없다고 말하기 전에" 절을 따른다.

## 그릴 화면을 정할 때 (디어 2026-09-21 확정)

프레임 목록을 짜기 전에 **과업 성격부터 판정한다.**

| 성격 | 그리는 범위 |
|---|---|
| 신규 구축 | 상태 화면을 포함해 전부 |
| **기존 서비스 개선** | **이번 개편으로 달라지는 화면만** |

기존 개선인데 상태 화면을 채우면 리뷰어가 "이것도 바뀌나" 하고 읽는다. 개발자는 이미 있는 것을 다시 만든다.

### 화면마다 한 줄을 답한다

목록에 올리는 화면마다 **"이번 개편으로 무엇이 달라지는가"** 를 한 줄로 쓴다. 못 쓰면 목록에서 빼고 사용자에게 확인한다.

```
1.1_주문배송목록_접힘        그룹핑 신설
1.2_주문배송목록_펼침        그룹핑 신설
2.7_검색시트_스크롤하단      상태가 11종으로 늘어 한 화면에 안 들어감
1.3_주문배송목록_Empty       ???  → 못 씀. 뺀다
```

### PRD에 없다는 것은 범위 밖이라는 뜻이다

**PRD가 빠뜨렸다는 뜻이 아니다.** 2026-09-21 주문배송목록에서 와이어 주석에 `PRD에 없는 화면` 이라고 Empty, Error, 스켈레톤 모두에 직접 써 놓고도 "PRD가 빠뜨렸으니 내가 채운다"로 읽었다. 셋 다 프로덕션에 이미 있고 이번 개편과 무관했다. 그려 놓고 전부 지웠다.

정말 PRD가 빠뜨린 것 같으면 **그리지 말고 확인 항목으로 올린다.** 그리는 것과 묻는 것은 다르다.

### 도달하지 않는 상태는 그리지 않는다

같은 날 캘린더 제약 위반 스낵바도 그렸다가 지웠다. 시작일을 고르면 유효하지 않은 날짜가 전부 비활성이라 그 스낵바가 뜰 경로 자체가 없었다. **폴백이라도 화면으로 만들면 있는 줄 안다.** 주석으로 남기고 화면은 만들지 않는다.

### state-verifier 결과를 그대로 프레임으로 만들지 않는다

`state-verifier` 는 Loading, Empty, Error, Disabled를 스캔해 누락을 올려 준다. **신규 화면 설계용 체크리스트다.** 기존 개선 과업에서는 그 목록에 "이번 개편으로 달라지는가" 필터를 한 번 더 건다.

### 범위 밖은 지우지 말고 이유를 남긴다

목록에서 뺀 화면은 케이스 문서에 남기되 **왜 안 그리는지** 적는다. 지우면 다음 사람이 또 올린다.

**PreToolUse hook `~/.claude/hooks/figma-guard.py` 가 금지 4로 차단한다.** 프레임이나 레이어 이름에 Empty, Error, Skeleton, 스켈레톤, Loading, 스낵바가 들어가면서 노드를 만들면 멈춘다. 범위 안이 확실하면 `ALLOW_STATE_SCREEN` 주석으로 통과시킨다.

## 확정된 스펙만 그린다 (디어 2026-09-21 확정)

**전달물에는 확정된 스펙만 들어간다.** 미확정을 그려 두면 리뷰어와 개발이 확정된 줄 안다. 지우는 비용보다 잘못 전달되는 비용이 크다.

### 미확정 신호

PRD 본문에 아래 꼬리표가 붙어 있으면 그 항목은 아직 스펙이 아니다.

| 신호 | 예 |
|---|---|
| 가능여부 확인 | `결제영수증 이미지 제공 가능여부 확인 [POS]` |
| 확인 후 결정 | `POS 교환/반품 사유 수집 기능 확인 후 제공여부 결정` |
| 외부 솔루션 미지원 | `바코드 값이나 이미지를 API로 내려주는 경로는 현재 지원되지 않습니다` |
| TBD, 미정, 협의 필요 | `무빙패스 TBD` |
| spec out | `[2026.07.27] spec out` |

**외부 의존이 특히 위험하다.** 솔루션사가 데이터를 안 내려주면 화면이 아무리 예뻐도 구현이 안 된다.

### 판단이 흔들릴 때

같은 PRD 안에서 **본문과 각주가 어긋나는 경우**가 있다. 2026-09-21 구매 영수증이 그랬다. 본문은 `선택 시 지류 영수증 이미지 조회 가능` 인데, 바로 아래 솔루션사 답변은 `이미지 파일로 전달하는 기능은 현재 지원되지 않습니다` 였다.

이때 **본문을 근거로 그리지 않는다.** 둘이 어긋난다는 것 자체가 미확정이라는 뜻이다.

다른 조항에서 그 기능이 필요한 이유를 발견하더라도 마찬가지다. 같은 날 결제 바코드를 두고 반품 조항에서 `지류 영수증 분실 시 App 내 주문내역으로 갈음` 을 찾아내 "필요한 이유가 있다"고 보고했는데, **필요한 이유가 있다는 것과 스펙이 확정됐다는 것은 다르다.** 근거를 찾았다고 그려도 된다는 뜻이 아니다.

### 처리 방법: 지우지 말고 격리한다 (디어 확정)

미확정 화면을 **전달 섹션 안에 두지 않는다.** 그렇다고 지우지도 않는다. **`PRD 확정 후 진행 예정` 섹션을 따로 만들어 거기에 모은다.**

| | 값 |
|---|---|
| 섹션 이름 | `PRD 확정 후 진행 예정` |
| 배경 | `#444444` |
| 테두리 | `#F05656` 3px |

다른 섹션은 배경 `#2B2B2B` 또는 `#151515` 에 테두리가 흰색 10% 1px 이다. **빨간 테두리가 이 섹션만의 표시**라서 멀리서 봐도 구분된다.

```js
const s = figma.createSection();
s.name = "PRD 확정 후 진행 예정";
s.fills = [{ type: "SOLID", color: { r: 0.267, g: 0.267, b: 0.267 } }];
s.strokes = [{ type: "SOLID", color: { r: 0.941, g: 0.337, b: 0.337 } }];
s.strokeWeight = 3;
```

- 전달 섹션에서 **빼서 이 섹션으로 옮긴다.** 지우면 다음에 또 처음부터 판단해야 한다
- 답이 오면 전달 섹션으로 되돌리고 프레임 번호를 다시 당긴다
- 화면 안의 일부 항목만 미확정이면 화면은 두고 **주석의 `확인 중(TBD)` 블록**에 적는다 (아래 "핸드오프 주석" 절)

**PreToolUse hook `~/.claude/hooks/figma-guard.py` 가 금지 5로 차단한다.** 프레임이나 레이어 이름에 TBD, 미정, 미확정, 확인필요, 협의중, 검토중이 들어가면서 노드를 만들면 멈춘다. **빨간 격리 섹션에 두는 경우라면 `ALLOW_TBD_SCREEN` 주석으로 통과시킨다.**

## 작화 전에 스펙을 다시 대조한다 (디어 2026-09-21 확정)

**프레임을 채우기 시작하기 직전에, 내가 이미 정리해 둔 스펙 요약을 다시 펼쳐 읽는다.** 요약을 작성한 기억이 있다고 해서 그 내용이 화면에 반영되는 것은 아니다.

**Why:** 2026-09-21 주문배송목록에서, 케이스 정의표의 확정 스펙 요약에 `검색 input: 타이틀 영역 돋보기 아이콘으로 간소화` 라고 **직접 써 놓고도** 검색창을 타이틀 아래 줄에 그대로 뒀다. 그건 AS-IS였다. 디어가 "탑바도 와이어프레임처럼 바꿔야지"라고 짚어줄 때까지 8개 프레임이 전부 틀린 채로 서 있었다. 요약을 쓴 것과 요약대로 그리는 것 사이에 아무 연결이 없었던 것이다.

### 대조하는 법

읽기만 하면 또 놓친다. **요약의 줄 하나하나를 화면 어디에 반영했는지 짚는다.**

| 상태 | 처리 |
|---|---|
| 요약에 있고 화면에도 있다 | 넘어간다 |
| 요약에 있는데 화면에 없다 | **멈추고 반영한다.** 반영이 불가능하면 확인 항목으로 올린다 |
| 화면에 있는데 요약에 없다 | 내가 지어냈을 가능성이 있다. 출처를 되짚는다 |
| 요약끼리 어긋난다 | 원문을 연다. 요약이 아니라 원문이 SSOT다 |

### 원문을 여는 것을 아끼지 않는다

요약은 내가 만든 2차 자료다. 조금이라도 막히면 **원문을 검색해서 확인한다.** 2026-09-21에 펼치기 어포던스를 확인 질문으로 올리려다 PRD를 검색했더니 `[총 N건 주문 펼쳐보기] CTA` 가 본문에 그대로 있었다. 같은 검색에서 `총 N건` 표기, 스낵바 문구, 탑바 돋보기가 전부 나왔다. 물어보기 전에 한 번 더 찾는다.

문서가 커서 한 번에 못 읽으면 툴이 저장한 파일을 키워드로 검색한다. 프로젝트 폴더의 `references.md` 에 문서 ID와 읽는 법이 적혀 있는 경우가 많다.

## 컴포넌트부터 찾는다 (디어 2026-09-21 확정)

프레임 골격을 세운 뒤 **화면 내부를 채우는 단계**에서 지킨다. 이 스킬의 기본은 내부를 비우는 것이지만, 사용자가 채우라고 지시하면 아래 순서로만 채운다.

**원칙: 이미 있는 화면의 컴포넌트를 그대로 가져온다. 비슷하게 생긴 것을 새로 그리지 않는다.**

### 채우기 전에 반드시 하는 일

참고 화면(같은 서비스의 기존 작업 파일)이 있으면 **거기 쓰인 인스턴스를 전수로 훑어서 목록을 먼저 만든다.**

```js
const root = await figma.getNodeByIdAsync("REF_FRAME_ID");
const seen = {};
const walk = async (n) => {
  if (n.type === "INSTANCE") {
    const mc = await n.getMainComponentAsync();
    if (mc) {
      const set = mc.parent && mc.parent.type === "COMPONENT_SET" ? mc.parent : null;
      const label = set ? set.name : mc.name;
      if (!seen[label]) seen[label] = {
        instId: n.id, w: Math.round(n.width), h: Math.round(n.height),
        mcKey: mc.key, mcRemote: mc.remote,
        setKey: set ? set.key : null, isSet: !!set };
    }
  }
  if ("children" in n) for (const c of n.children) await walk(c);
};
await walk(root);
return seen;
```

이 목록이 **그려야 할 화면의 부품 명세**다. 목록을 손에 쥐기 전에는 한 줄도 그리지 않는다.

#### 참고 화면 안에도 컴포넌트가 아닌 것이 섞여 있다

**`INSTANCE` 만 세면 놓친다.** 참고 화면이라고 해서 안의 모든 것이 컴포넌트인 것은 아니다. 아이콘 자리에 기호 문자를 타이핑해 둔 경우가 흔하다.

```js
// 아이콘 대신 쓰인 기호 텍스트를 같이 찾는다
const GLYPH = /^[\u2302\u2315\u2039\u203A\u2715\u00D7\u2713\u2304\u2303\u2190-\u2193\u2261]+$/;
const suspects = root.findAll(n => n.type === "TEXT" && GLYPH.test(String(n.characters).trim()));
return suspects.map(n => n.id + " " + n.characters + " @" + n.parent.name);
```

2026-09-22에 PC AS-IS 화면의 검색창 돋보기가 **아이콘 컴포넌트가 아니라 문자 하나**였다. 300 폭일 때는 티가 안 났는데 검색창을 1192로 늘리자 아이콘만 그대로 작아 눈에 띄었다. 그 전에도 손으로 그린 와이어에 `‹` 와 `⌕` 를 문자로 찍은 전례가 있었다.

**문자로 된 아이콘을 발견하면 Icon Library에서 대응 컴포넌트로 바꾼다.** AS-IS 프레임은 현행 그대로 두고 TO-BE 프레임만 교체한다.

#### 아이콘만 바꾸고 껍데기를 두지 않는다

문자 아이콘을 찾았으면 **그 아이콘이 들어 있는 덩어리 자체가 컴포넌트인지** 본다. 아이콘만 갈아끼우면 프레임은 여전히 손으로 만든 것이다.

```js
// 컴포넌트가 아닌 채로 남아 있는 UI 덩어리를 찾는다
// root 는 화면 전체가 아니라 "이번에 손댄 영역"을 넣는다
const UI = /(input|search|field|button|btn|chip|tab|badge|toggle|select|dropdown|검색|버튼|칩|탭|뱃지)/i;
const inInst = (x) => { while (x) { if (x.type === "INSTANCE") return true; x = x.parent; } return false; };
const isWrapper = (n) => n.children.length > 0 && n.children.every(c => c.type === "INSTANCE");
const orphans = root.findAll(n =>
  n.type === "FRAME" && UI.test(n.name) && !inInst(n) && !isWrapper(n)
);
return orphans.map(n => n.id + " " + n.name + " " + Math.round(n.width) + "x" + Math.round(n.height));
```

**`root` 를 화면 전체로 두면 오탐이 쏟아진다.** AS-IS에서 복제해 온 영역(GNB, 탭 바, 사이드바)이 전부 걸리는데 그것들은 이번 개편 대상이 아니라 손대면 안 된다. **이번에 바꾼 영역만 넣는다.**

자식이 전부 `INSTANCE` 인 프레임은 배치용 컨테이너이므로 제외한다. ODS 칩 여러 개를 담은 토글 줄 같은 것이다.

2026-09-22에 PC 검색창이 그랬다. `search` 프레임 구조가 `FRAME + TEXT + 문자` 인 것을 **읽어서 알고 있었는데도 아이콘만 교체**하고 넘어갔다. ODS에 `🌀 Search Field` 가 있었고 `[✅ Web 사용가능]` 이었다.

같은 하루에 세 번 반복했다. 주문 카드를 손으로 그린 것, PC 모달을 모바일 시트 복제로 만든 것, 검색창 아이콘만 바꾼 것. 셋 다 **눈에 보이는 문제만 고치고 그 요소가 컴포넌트인지는 보지 않은 것**이다.


### 가져오는 순서

1. **`importComponentByKeyAsync`**: 단일 `COMPONENT` 키. 세트 키를 넣으면 실패한다
2. **`importComponentSetByKeyAsync`**: `COMPONENT_SET` 키. 세트를 받아 원하는 variant를 골라 `createInstance()`
3. 대상 파일에 **같은 컴포넌트 인스턴스가 이미 있으면 `clone()`**. 마스터 연결이 유지된다
4. 셋 다 안 되면 **멈추고 사용자에게 요청한다.** 아래 절차

### 플랫폼별로 어느 라이브러리를 보는가 (디어 2026-09-22 확정)

**ODS가 Web도 커버한다. PC 화면이라고 다른 디자인 시스템을 찾지 않는다.**

컴포넌트 설명에 플랫폼 표기가 있다. 이것을 먼저 읽는다.

```
[✅ Android/iOS 사용가능]
[✅ Web 사용가능]          ← PC와 MW 모두 이 컴포넌트를 쓴다
[❌ Web 사용불가]
[👉Web은 BDS Textarea 를 사용해주세요]   ← 이럴 때만 BDS로 간다
```

`🪣 Bucketplace Design System` (BDS)는 **ODS로 통합되는 중**이다. Empty Page, FixedTab, Chip이 전부 `[Deprecated] ODS를 사용해주세요` 다. BDS에서 찾다가 없다고 결론내지 않는다.

#### 이름이 맞아도 트랙이 다르면 다른 서비스다 (디어 2026-09-22 확정)

`search_design_system` 결과에서 **`libraryName` 을 이름보다 먼저 읽는다.**

| 라이브러리 | 무엇 |
|---|---|
| `🌀 ODS (Ohouse Design System)` | 국내 공통. 기본값 |
| `🌐 Global Track Component` | **해외 서비스(O!House)**. 국내 화면에 쓰면 안 됨 |
| `O2O Track Component` / `Growth Track Component` / `[Creator] ...` | 각 트랙 전용 |
| `Ohouse Track Component` | 국내지만 특정 지면 전용. 공통으로 착각하지 말 것 |

2026-09-22에 웹 GNB를 찾다가 `web_GNB` 를 발견하고 그대로 넣었다. 🌐 Global Track 소속이라 화면에 **O!House 로고와 Explore 메뉴**가 떴다. 스크린샷을 찍고서야 알았다.

**이름이 일치한다고 채택하지 않는다.** `libraryName` 을 확인하고, 배치한 뒤 `get_screenshot` 으로 로고와 메뉴 문구를 눈으로 본다.

2026-09-22에 PC 검색 모달을 만들면서 "PC용 ODS가 없다"고 단정하고 모바일 시트를 복제해 썼다. 확인해 보니 `🌀 Bottom Sheet` 에 `[✅ Web 사용가능]` 이 붙어 있었다. **찾아보지 않고 없다고 말한 것이다.**

#### 모바일 전체 화면 컴포넌트를 PC에 쓸 때

`🌀 Bottom Sheet` 는 Web 사용가능이지만 **컴포넌트 자체가 모바일 375 전체 화면**이다. 안에 상단 스테이터스바, Dim, 홈 인디케이터 둘, 핸들이 들어 있다.

PC 모달로 쓸 때는 그 다섯을 숨기고 `Main` 만 남긴다. 남은 `Handle / Header / Content 슬롯 / Footer` 가 ODS 구조 그대로다.

| 처리 | 이유 |
|---|---|
| 상단 스테이터스바 숨김 | PC에 없음 |
| Dim 숨김 | 375 폭이라 PC 뷰포트를 못 덮음. 따로 전체 폭 Dim을 깐다 |
| 홈 인디케이터 둘 숨김 | PC에 없음 |
| Handle 숨김 | 바텀시트 어포던스. PC 모달에는 없음 |

**슬롯에는 패딩이 없다.** 내용을 옮기면 좌우가 모달 가장자리에 붙는다. `paddingLeft` 와 `paddingRight` 를 직접 준다.

### 없다고 말하기 전에 (디어 2026-09-22 확정)

**"이 파일에 없다"는 결론은 전 페이지를 훑은 뒤에만 낸다.** 작업 중인 섹션만 보고 말하지 않는다.

```js
const RE = /(찾을이름|다른후보|또다른후보)/;
const hits = [];
const walk = (n, pg, d) => {
  if (hits.length >= 30) return;
  if (RE.test(n.name)) hits.push(pg + " | " + n.id + " | " + n.type + " | " + n.name.slice(0, 32));
  if (d < 7 && "children" in n) for (const c of n.children) walk(c, pg, d + 1);
};
for (const p of figma.root.children) {
  await p.loadAsync();
  for (const c of p.children) walk(c, p.name.slice(0, 10), 0);
}
return hits;
```

2026-09-22에 모바일웹 GNB를 찾으면서 전달 섹션만 보고 "이 파일에는 웹 내비가 없다"고 두 번 말했다. 실제로는 **02 페이지 주문배송목록 과업에 `top/프로덕션동일` 이 통째로 있었고**, GNB와 푸터는 캡처 이미지로 깔려 있었다. 같은 파일 안 다른 과업 페이지에 이미 그려둔 지면이 있는 경우가 많다.

**이미지 캡처도 같이 찾는다.** 컴포넌트가 없어도 캡처가 있으면 그게 답이다.

```js
// IMAGE 채우기를 가진 노드를 폭으로 걸러 찾기
let f = null;
try { f = n.fills === figma.mixed ? null : n.fills; } catch (e) {}
if (f && f.some(x => x.type === "IMAGE") && n.width > 800) { /* PC 폭 캡처 */ }
```

### 인스턴스 폭을 바꿀 때 (디어 2026-09-22 확정)

**폭만 바꾸면 자식이 원래 폭에 고정된 채 남는다.** 오토레이아웃이라 따라올 것 같지만 `FIXED` 인 자식은 안 따라온다.

2026-09-22에 PDP 오프라인 모듈을 343에서 474로 늘렸다. 겉보기 폭은 474가 됐는데 안쪽 `Title` 이 317에 그대로 있었다. `Title` 이 `SPACE_BETWEEN` 이라 **펼침 화살표가 화면 가운데에 떠 있었다.** 디어가 짚어줄 때까지 몰랐다.

폭을 바꾼 직후 이걸 돌린다.

```js
const fix = (n, d) => {
  if (d > 3 || !("children" in n)) return;
  for (const c of n.children) {
    if ((c.type === "FRAME" || c.type === "INSTANCE") && c.layoutSizingHorizontal === "FIXED") {
      const avail = n.width - (n.paddingLeft || 0) - (n.paddingRight || 0);
      if (n.layoutMode === "VERTICAL" && c.width < avail - 1) {
        try { c.layoutSizingHorizontal = "FILL"; } catch (e) {}
      }
    }
    fix(c, d + 1);
  }
};
```

**한 프레임만 고치지 않는다.** 같은 컴포넌트를 쓴 프레임 전수를 돌리고, 고치기 전후 자식 폭을 같이 반환해서 무엇이 바뀌었는지 남긴다.

### 임포트가 실패할 때 원인 가려내기

`Component with key ... not found` 는 원인이 여러 가지다. **추측하지 말고 순서대로 확인한다.**

| 확인 | 방법 | 실패의 의미 |
|---|---|---|
| 1. 키 종류가 맞나 | 단일은 `importComponentByKeyAsync`, 세트는 `importComponentSetByKeyAsync` | 함수를 바꾸면 바로 풀린다 |
| 2. 라이브러리가 붙어 있나 | `get_libraries` 를 **두 파일 모두** 호출해 `libraries_added_to_file` 대조 | 대상 파일에만 없으면 사용자가 붙이면 된다 |
| 3. 퍼블리시된 라이브러리에 있나 | `search_design_system` 에 `includeLibraryKeys` 로 후보 라이브러리를 좁혀 검색 | 어디에도 안 나오면 팀 라이브러리 컴포넌트가 아니다 |

**3번까지 왔는데 안 나오면 그 컴포넌트는 퍼블리시된 라이브러리 소속이 아니다.** 참고 파일 안에 인스턴스로만 살아 있는 것이다. Figma는 **이미 배치된 인스턴스는 구독이 끊겨도 유지**하므로, 참고 파일에서 멀쩡히 보인다고 해서 가져올 수 있다는 뜻이 아니다.

이때 사용자에게 이렇게 요청한다. **컴포넌트 하나가 아니라 그 컴포넌트가 실제로 쓰인 화면 한 장을 통째로 달라고 한다.**

> `{컴포넌트명}` 이 들어간 화면 프레임을 통째로 하나 복사해서 대상 파일 아무 데나 붙여주세요. 거기서 복제해 쓰겠습니다.

붙여주면 `clone()` 으로 쓴다. **컴포넌트를 직접 만들어 흉내내지 않는다.** 원본과 어긋나고 나중에 동기화도 안 된다.

#### 왜 컴포넌트 하나가 아니라 화면 한 장인가 (디어 2026-09-21 확정)

컴포넌트만 받으면 부품은 맞는데 조립이 틀린다. **화면에는 컴포넌트에 없는 것이 들어 있다.**

| 화면에만 있는 것 | 예 |
|---|---|
| 컴포넌트 사이의 배치와 계층 | 카드 그룹 = `card_grouping` 1개 + `OrderCard` N개 + `Divider` |
| 상태 토글 구조 | `OrderCard` 안에 주문상태 8종이 `visible` 토글로 들어 있음 |
| 실제 여백과 auto-layout 설정 | 시트 본문이 `clipsContent: true` 라 자식을 숨기면 스크롤이 표현됨 |
| 프로덕션 문구와 더미 데이터 | 상태행 문구, 옵션 표기, 가격 형식 |
| 어느 컴포넌트가 세트고 어느 것이 단일인지 | 키 종류를 틀리지 않게 됨 |

2026-09-21 주문배송목록에서 카드 컴포넌트 세 개를 임포트하려다 전부 실패했고, 디어가 선물하기 목록 화면을 인스턴스가 살아 있는 채로 통째로 붙여주자 작업이 **만들기에서 고르기로 바뀌었다.** 특히 `OrderCard` 안에 상태 8종이 이미 토글로 들어 있던 것은 컴포넌트만 받아서는 알 수 없었다. 손으로 그렸다면 8종을 새로 만들면서 하나씩 틀렸을 것이다.

화면을 받으면 **채우기 전에 반드시 인스턴스를 전수로 훑고**(위 스크립트), 이어서 **상태 토글 구조를 확인한다.** 상태가 이미 들어 있으면 케이스 작업은 `visible` 전환으로 끝난다.

받은 화면에 없는 상태가 있으면 그것부터 사용자에게 말한다. 주문 카드에 취소와 교환과 반품이 없었던 것이 그런 경우였고, 원본은 다른 상태 슬롯의 문구를 바꿔 쓰고 있었다.

### 손으로 그려도 되는 것

| 그려도 됨 | 반드시 컴포넌트 |
|---|---|
| 빈 프레임, 구분용 배경 면 | 카드, 버튼, 뱃지, 칩, 인풋, 탑내비, 디바이더 |
| 주석과 라벨 텍스트 | 화면 안에 들어가는 모든 텍스트 (등록된 텍스트 스타일 필수) |
| 아직 컴포넌트가 없는 신규 모듈 | 아이콘 |

**신규 모듈이라 컴포넌트가 없다고 판단했으면 그 판단부터 사용자에게 확인받는다.** 검색어 하나로 없다고 단정하지 않는다. 이름 후보를 셋 이상 바꿔가며 찾는다.

## 프로덕션 캡처로 PC 화면을 만든다 (디어 2026-09-22 확정)

2026-09-22에 이 요청을 안 하고 PDP PC를 부품으로 조립했다. 갤러리는 카드 썸네일의 이미지 채우기를 재활용하고, 우측 컬럼은 모바일 ATF 블록을 늘려 붙였다. 디어가 실물 캡처를 붙여주자 **통째로 버렸다.**

### 캡처 위에 새 모듈을 끼우는 법

캡처는 정지 이미지라 모듈을 그냥 얹으면 아래 내용이 가려지고, 흰 마스크로 덮으면 그 영역이 사라진다. **둘 다 틀렸다.**

**캡처를 세 조각으로 자르고 바뀌는 컬럼만 내린다.**

```
상단 전체        (0, 0, W, SPLIT_Y)
좌측 하단        (0, SPLIT_Y, SPLIT_X, H - SPLIT_Y)        그대로
새 모듈          (COL_X, SPLIT_Y + GAP)
우측 하단        (SPLIT_X, SPLIT_Y + shift, W - SPLIT_X, H - SPLIT_Y)
shift = 모듈 높이 + GAP * 2
```

각 조각은 `clipsContent: true` 프레임에 캡처 클론을 음수 좌표로 넣어 만든다.

```js
const crop = (name, x, y, w, h, ix, iy) => {
  const f = figma.createFrame();
  f.name = name; f.clipsContent = true; f.fills = [];
  F.appendChild(f); f.resize(w, h); f.x = x; f.y = y;
  const img = capSrc.clone();
  f.appendChild(img); img.resize(W, H); img.x = ix; img.y = iy;
};
```

- **자르는 경계는 여백 줄에 둔다.** 요소 중간을 자르면 반쪽이 보인다
- 프레임 높이는 `SPLIT_Y + shift + (H - SPLIT_Y)` 로 늘린다
- 모듈은 마지막에 `appendChild` 해서 캡처 조각 위로 올린다

### 간격은 px이 아니라 비율로 옮긴다

캡처마다 배율과 뷰포트가 달라 실측 px을 그대로 쓰면 어긋난다. **GNB 높이를 기준으로 비율을 낸다.**

2026-09-22 실측: 웹 마이페이지의 오너 내비와 2depth 내비는 각각 **GNB 높이의 0.71** 이다. GNB 81짜리 캡처에서는 두 줄 다 57이 된다.

| 지면 | 실측 |
|---|---|
| PC 웹 | GNB 81, 오너 내비 57, 2depth 57, 2depth는 **가운데 정렬** |
| 모바일웹 | GNB 47, 오너 내비 51, 페이지 내비 57(가로 스크롤), 오너 내비는 3개(나의 리뷰 없음) |

### 앱과 웹은 섹션을 나누고, MW와 PC는 한 행에

행 = 지면 규칙은 그대로다. 여기에 한 겹을 더한다.

- 섹션 이름은 `[Mobile] {과업명}` 과 `[Web] {과업명}` 으로 짝을 맞춘다

## 핸드오프 주석 (디어 파일 실측 2026-09-21)

화면을 다 그린 뒤 개발 전달용 주석을 붙이는 단계. 기준은 `01. 온/오프 스토어커넥트` 페이지에서 실측한 값이다.

### 위치

```
[프레임 375]  40  [주석]
```

- **주석 x = 프레임 우측 끝 + 40**
- 주석 y는 가리키는 요소의 세로 위치에 맞춘다. 프레임 상단이 아니다
- 한 프레임에 여러 건이면 **세로로 쌓는다** (실측 3건까지)
- 주석에서 해당 요소로 **리더 라인**을 긋는다: `VECTOR`, 흰색 60%, 두께 1.5, `strokeCap = "TRIANGLE_FILLED"`

### 스타일

| 요소 | 값 |
|---|---|
| 텍스트 스타일 | `Body14L20_Regular` (Pretendard 14, 행간 20) |
| 제목 줄 | Bold, `#00FF40` |
| 본문 | Regular, 흰색 |
| 리사이즈 | `textAutoResize = "WIDTH_AND_HEIGHT"` |
| 폭 | 기본 315. 내용이 많으면 546 또는 677 |

제목과 본문은 한 TEXT 노드 안에서 `setRangeFontName` 과 `setRangeFills` 로 나눈다. 노드를 둘로 쪼개지 않는다.

### 내용 구조와 서식

**제목 한 줄 + 불렛 목록**이다. 평문으로 줄만 나열하지 않는다. Figma 리스트 서식을 실제로 건다.

```
2. QR 스캔 기록                                   ← 제목. Bold, #00FF40
 •  기존 최근 본 상품 영역에 매장에서 QR을 스캔한 상품을 함께 표시
 •  QR을 스캔한 상품의 썸네일 좌측 하단에 매장명 뱃지 표시
 •  매장명은 고정 문구가 아닌 스캔한 매장 정보에 따른 변수로 처리
 •  온라인에서만 조회한 상품에는 매장 뱃지 미표시
확인 중(TBD)                                      ← Bold, 흰색, 리스트 없음
 •  아직 정해지지 않은 항목
```

| 줄 | 리스트 | 폰트 | 색 | 들여쓰기 |
|---|---|---|---|---|
| 제목 | `ORDERED` 또는 `NONE` | Bold | `#00FF40` | 1 |
| 본문 | `UNORDERED` | Regular | 흰색 | 1 |
| `확인 중(TBD)` | `NONE` | Bold | 흰색 | 1 |
| TBD 항목 | `UNORDERED` | Regular | 흰색 | 1 |

```js
t.setRangeListOptions(start, end, { type: "UNORDERED" });
t.setRangeIndentation(start, end, 1);
```

### 제목에 번호를 매기는 기준 (디어 확정)

| 상황 | 제목 리스트 |
|---|---|
| **한 화면에 정의가 여러 개** | `ORDERED` |
| **단일 스펙** | `NONE` |

실측이 정확히 갈렸다. 화면당 주석이 하나인 것은 전부 `NONE` 이었고, 한 화면에 셋이 붙은 것은 전부 `ORDERED` 였다. **번호를 글자로 직접 쓰지 않는다.** 서식으로 건다.

### 본문에 적는 것

- **조건과 동작만 적는다.** 디자인 의도나 근거는 적지 않는다. 실측한 항목은 노출 조건, 표시 내용, 버튼 동작, 플랫폼 분기가 전부였다
- 소제목을 두지 않는다. 항목이 많으면 **주석을 쪼개고 번호를 매긴다**
- 플랫폼이 갈리면 그 줄에서 갈라 적는다 (`iOS 앱 비로그인 사용자:`, `Android 앱은`)
- **미확정은 맨 아래 `확인 중(TBD)` 블록**에 모은다. 본문에 섞지 않는다

### 케이스가 많으면 표로 뺀다

케이스가 대여섯을 넘으면 주석으로 감당이 안 된다. **별도 섹션에 표를 만든다.**

- 섹션 이름 예: `PDP 오프라인 모듈 / 케이스별 스펙`, 배경 `#151515`
- 상단에 공통 스펙 블록을 두고 그 아래 표
- **행 = 항목**(노출 조건, 상태별 표시, 마이크로 카피), **열 = Case 1..N**

### 순서

주석은 **화면이 확정된 뒤에** 붙인다. 화면이 흔들리는 동안 붙이면 좌표와 내용을 두 번 고친다.

### 끝내기 전에 센다

**누락은 코드에 흔적이 없어서 사전에 못 막는다. 숫자로 센다.**

```js
const sec = await figma.getNodeByIdAsync("SECTION_ID");
const notes = sec.children.filter(c => c.type === "TEXT" && c.name.indexOf("주석_") === 0);
const leads = sec.children.filter(c => c.type === "VECTOR" && c.name.indexOf("리더_") === 0);
const frames = sec.children.filter(c => c.type === "FRAME" && Math.round(c.width) === 375 && c.name !== "template");
const bars = sec.children.filter(c => c.name === "Title" && Math.round(c.width) === 375);
return {
  주석: notes.length, 리더: leads.length, 짝: notes.length === leads.length,
  프레임: frames.length, 케이스바: bars.length, 짝2: frames.length === bars.length,
  피치부족: frames.map(f => Math.round(f.x)).sort((a,b)=>a-b)
    .some((x, i, arr) => i > 0 && x - arr[i-1] < 860)
};
```

- **주석 개수 = 리더 라인 개수**
- **프레임 개수 = 케이스 바 개수**
- 주석을 붙일 행은 **프레임 피치가 (프레임 폭 + 485) 이상**이어야 한다 (간격 40 + 주석 315 + 여백 130)
- 전달 섹션에 미확정 프레임이 남아 있지 않은가
- **이번에 바꾼 영역에 컴포넌트가 아닌 UI 덩어리가 남아 있지 않은가** (위 orphans 스크립트. 화면 전체가 아니라 손댄 영역만 넣는다)

숫자가 안 맞으면 기억과 무관하게 드러난다. 2026-09-21에 리더 라인을 스킬에 적어 놓고도 빼먹었다.

### 숫자가 맞아도 눈으로 본다

**좌표 실측이 정상인데 화면은 깨져 있을 수 있다.** 세 번 겪었다.

| 실측 결과 | 실제 화면 |
|---|---|
| 슬롯 자식이 `기간@x0`, 폭 500, FILL | 슬롯에 패딩이 0이라 글자가 모달 밖으로 나감 |
| Empty 인스턴스 `sizing=FILL` | 컴포넌트가 343 고정 폭이라 좌측에 붙음 |
| 루트 프레임 폭 375로 변경 완료 | 내부가 393 그대로라 우측이 잘림 |

셋 다 **`get_screenshot` 으로 그 노드를 찍어 봤으면 즉시 보였다.** 실측은 값이 맞는지만 알려주고 보이는 결과는 알려주지 않는다.

**작업 단위마다 결과 노드를 찍는다.** 프레임 전체가 크면 방금 손댄 노드만 찍는다. 섹션 전체 축소 스크린샷으로는 이런 것이 안 보인다.

### 주석 위치도 센다

개수만 세면 **좌표가 틀린 것은 안 걸린다.** 같은 날 PC 주석 네 개를 모바일 기준 y로 찍어서 가리키는 요소보다 한참 위에 떠 있었는데, 개수는 4대 4로 맞아서 통과했다.

**주석 y가 그 프레임 안 어떤 요소의 y와도 맞닿지 않으면 의심한다.**

**소속 프레임은 좌표가 아니라 이름의 번호로 찾는다.** 좌표로 역산하면 어긋난 주석이 옆 프레임에 매칭돼 **통과로 나온다.**

```js
const sec = await figma.getNodeByIdAsync("SECTION_ID");
const sa = sec.absoluteBoundingBox;
const rel = (n) => Math.round(n.absoluteBoundingBox.y - sa.y);
const key = (s) => { const m = s.match(/(\d+\.\d+)/); return m ? m[1] : null; };
const frames = sec.children.filter(c => c.type === "FRAME" && c.name !== "template");
const notes = sec.children.filter(c => c.type === "TEXT" && c.name.indexOf("주석_") === 0);
const bad = [];
for (const t of notes) {
  // 이름의 번호로 짝을 먼저 정하고, 좌표가 규칙과 맞는지 확인한다
  const f = frames.filter(fr => key(fr.name) === key(t.name))[0];
  if (!f) { bad.push(t.name + " : 짝 프레임 없음"); continue; }
  if (Math.abs(t.x - (f.x + f.width + 40)) > 2) { bad.push(t.name + " : x 어긋남"); continue; }
  if (t.y < f.y - 60 || t.y > f.y + f.height) { bad.push(t.name + " : y 범위 밖"); continue; }
  let best = Infinity;
  const walk = (n) => {
    if (n.visible && n.absoluteBoundingBox) best = Math.min(best, Math.abs(rel(n) - t.y));
    if ("children" in n) for (const c of n.children) walk(c);
  };
  walk(f);
  if (best > 40) bad.push(t.name + " : 가장 가까운 요소와 " + best + "px 차이");
}
return bad.length ? bad : "주석 위치 이상 없음";
```

**좌표로 소속을 역산하면 안 된다.** 2026-09-22 에 01행 주석 네 개가 프레임보다 560 왼쪽에 있었는데, 그 자리가 마침 AS-IS 프레임의 주석 열이라 검증이 전부 통과로 나왔다. 화면에서는 1.1 설명이 AS-IS 옆에 붙어 AS-IS 설명으로 읽혔다. 이름 기준으로 바꾸면 이런 것이 `x 어긋남` 으로 바로 잡힌다.

이름 기준은 덤으로 **프레임 번호를 다시 매겼는데 주석 이름을 안 바꾼 경우**도 `짝 프레임 없음` 으로 잡아 준다. 행을 재편하면 주석과 리더 이름도 같이 바꾼다.

**리더 라인도 같은 규칙으로 센다.** 리더 x 는 주석 x 에서 20 을 뺀 값이다. 주석만 옮기고 리더를 두면 선이 딴 데 남는다.

### 그룹 바 폭도 센다

그룹 바는 **그 행의 프레임을 정확히 덮어야 한다.** AS-IS 프레임은 그룹 밖이라 빼고 센다.

```js
const row = frames.filter(f => Math.abs(f.y - (bar.y + 266)) < 40 && f.name.indexOf("AS-IS") !== 0);
let mn = Infinity, mx = -Infinity;
for (const f of row) { mn = Math.min(mn, f.x); mx = Math.max(mx, f.x + f.width); }
bar.x = mn; bar.resize(mx - mn, 60);
```

프레임을 지우거나 열을 당기면 바는 따라오지 않는다. 2026-09-22 에 네 섹션의 그룹 바가 전부 프레임 오른쪽 끝을 355 넘어가 있었고, 프레임 한 장을 지운 행은 시작점까지 860 밀려 있었다. **행을 손댈 때마다 이 스크립트를 돌린다.**

**주석 y를 숫자로 찍지 않는다.** 프레임 안에서 가리킬 요소를 찾아 `absoluteBoundingBox` 로 섹션 기준 y를 계산해 쓴다. 모바일 812 프레임과 PC 1975 프레임은 같은 요소라도 y가 두 배 넘게 차이난다.

## 실행 순서

### STEP 1. 읽기 점검 (참고 파일 + 대상 파일 병렬)

`use_figma`로 **읽기 전용** 스크립트를 두 파일에 각각 보낸다. 한 메시지에 두 개를 같이 보낸다.

참고 파일에서 확인할 것:

```js
// 섹션 배경, 자식 구조
const sec = await figma.getNodeByIdAsync("SECTION_ID");
const secFill = sec.fills !== figma.mixed ? sec.fills : null;
const kids = sec.children.slice(0, 40).map(c => ({ id: c.id, name: c.name, type: c.type,
  x: Math.round(c.x), y: Math.round(c.y), w: Math.round(c.width), h: Math.round(c.height) }));
return { secFill, kids };
```

그 다음 바 컴포넌트의 **key와 variant 목록**을 뽑는다. `INSTANCE`를 하나 잡아서:

```js
const inst = await figma.getNodeByIdAsync("INSTANCE_ID");
const mc = await inst.getMainComponentAsync();
const set = mc.parent;
return { key: mc.key, name: mc.name, remote: mc.remote,
  variants: set.type === "COMPONENT_SET" ? set.children.map(c => ({ name: c.name, key: c.key })) : [] };
```

대상 파일에서 확인할 것: 페이지 목록, 대상 페이지의 기존 노드, 폰트 가용성, 그리고 **컴포넌트 임포트가 되는지**.

```js
try { const c = await figma.importComponentByKeyAsync("KEY"); }
catch (e) { /* 퍼블리시 안 됨 → 사용자에게 알리고 대안 협의 */ }
```

**임포트가 실패하면 멈추고 물어본다.** 컴포넌트를 새로 만들지 말 것.

### STEP 2. 섹션 + 라벨 + 바

한 번의 `use_figma`로 만든다. 아직 프레임은 만들지 않는다.

- **섹션**: 참고 파일과 같은 배경색. `figma.createSection()` + `resizeWithoutConstraints(w, h)`
- **대주제 라벨**: **`template` 컴포넌트 인스턴스를 쓴다.** 텍스트로 직접 만들지 않는다. 내부 TEXT 한 개의 `characters`만 `{번호} {이름}` 한 줄로 교체한다 (예: `01 PDP 진입`)
- **그룹 바 / 케이스 바**: `Title` 컴포넌트 인스턴스. `createInstance()` → `resize(w, 60)` → 내부 TEXT의 `characters`만 교체

#### 컴포넌트를 못 가져올 때

`importComponentByKeyAsync`가 `Component with key ... not found`로 실패하는 경우가 있다. 퍼블리시 상태나 라이브러리 접근 권한 문제다. 이때는 **새로 만들지 말고 순서대로 시도한다.**

1. 대상 파일에 해당 컴포넌트 **인스턴스가 이미 있으면 `clone()`** 한다. 마스터 연결이 그대로 유지된다
   ```js
   const src = await figma.getNodeByIdAsync("INSTANCE_ID");
   const inst = src.clone();
   sec.appendChild(inst);
   inst.x = x; inst.y = y; inst.resize(w, h);
   ```
2. 인스턴스도 없으면 **사용자에게 그 컴포넌트가 쓰인 화면 한 장을 통째로 붙여달라고 요청**한다. 컴포넌트 하나만 받지 않는다. 이유는 위 "왜 컴포넌트 하나가 아니라 화면 한 장인가" 절
3. 컴포넌트를 직접 만들어 흉내내지 않는다. 원본과 어긋나고 나중에 동기화도 안 된다

### STEP 3. 빈 프레임

프레임은 **비워서** 만든다.

```js
const f = figma.createFrame();
f.name = "1.1_PDP_기본";   // 프레임명이 곧 전달물
f.resize(375, 812);
f.x = x; f.y = y;
f.fills = [{ type: "SOLID", color: { r: 1, g: 1, b: 1 } }];
sec.appendChild(f);
```

`layoutMode`를 설정하지 않는다. 자식을 넣지 않는다.

### STEP 4. 검증

`get_screenshot`으로 섹션 전체를 찍어 사용자에게 보여준다. 배치가 어긋났으면 그 부분만 고친다.

## 배치 규칙

기존 과업 파일에서 실측한 체계. 참고 파일의 파일 키와 노드 ID는 **대화에서 받는다.**

```
[대주제 라벨]  [AS-IS(회색)]  [Primary 그룹 바 ─────────────────]
 00                            [Default 케이스 바] [케이스 바] ...
 공통 상태      기존 화면        빈 프레임           빈 프레임
```

- **가로 = 케이스 전개, 세로 = 대주제 전환**
- AS-IS 참조는 행 맨 왼쪽. 기존 화면을 쓰는 행에만 둔다
- 케이스가 많은 행은 가로로 길어진다. 그대로 둔다

### 프레임을 언제 늘리나 (디어 2026-09-21 확정)

**화면 레벨에서 확인할 게 없고 케이스만 필요하면 프레임을 늘리지 않는다. 한 프레임 안에 케이스를 정의한다.**

판단 기준은 하나다. **이 케이스를 보려고 화면을 처음부터 다시 봐야 하는가.**

| 상황 | 처리 |
|---|---|
| 목록 화면에서 카드 종류만 다름 | 한 프레임에 카드를 여러 장 쌓는다. 1건 주문, CTA 세트가 다른 상태, 클레임 접수건, 특수 주문을 한 화면에 나열 |
| 상세 화면에서 행 하나 있고 없고 | 프레임을 나누지 않고 기본 프레임 주석에 적는다 |
| 같은 화면에서 선택 상태만 다름 | 대표 상태 한 장만 그리고 나머지는 주석 |
| 하단 콘텐츠가 밀리는 정도를 봐야 함 | 프레임을 나눈다 |
| 진입 경로가 달라 상단 구조가 바뀜 | 프레임을 나눈다 |
| 빈 상태, 에러, 스켈레톤 | 프레임을 나눈다 |

케이스를 한 화면에 쌓으면 프레임 높이가 812를 넘는다. **그 프레임만 높이를 늘린다.** 다른 프레임까지 같이 키우지 않는다.

상태가 아주 많은 모듈은 예외로 **모듈 셀 줄**을 쓴다. 375 폭 셀을 케이스 바 아래 한 줄로 모으고 그 줄을 상태 전수의 SSOT로 둔다. 풀 프레임을 상태 수만큼 반복하면 리뷰어가 차이를 못 찾는다.

### 텍스트 스타일 (디어 2026-09-21 확정)

**텍스트를 만들 때 크기와 굵기를 직접 찍지 않는다. 라이브러리에 등록된 텍스트 스타일을 찾아 물린다.**

ODS 텍스트 스케일은 세 계열이다. 이름은 `{계열}{크기}L{행간}_{굵기}` 꼴이다.

| 계열 | 크기 | 쓰는 곳 |
|---|---|---|
| Heading18 | 18 | 시트 타이틀, 화면 타이틀 |
| Body16, Body15, Body14 | 16, 15, 14 | 상단 내비 타이틀, 섹션 라벨, 본문, 버튼 |
| Detail13, Detail12, Detail11, Detail10 | 13, 12, 11, 10 | 보조 정보, 건수, 옵션명, 날짜, 캡션 |

굵기는 Bold, Semibold, Medium, Regular. 같은 크기에 행간이 둘 이상 있으므로(Body14L18 과 Body14L20) 줄이 하나면 짧은 행간, 여러 줄이면 긴 행간을 쓴다.

**찾는 순서**

1. `search_design_system` 의 `entity: "style"` 로 검색한다
2. **검색어 하나로 없다고 단정하지 않는다.** `Body` 로 검색하면 `Detail` 계열이 안 나온다. 크기가 안 보이면 계열 이름을 바꿔 다시 찾는다
3. 파일에 이미 쓰이는 스타일은 TEXT 노드의 `textStyleId` 를 모아 `getStyleByIdAsync` 로 이름과 크기를 확인하고 그 id 를 그대로 재사용한다
4. 파일에 없는 스타일은 `importStyleByKeyAsync(key)` 로 가져온 뒤 그 id 를 쓴다

**적용할 때**

- 그 스타일의 폰트를 먼저 로드한다. Pretendard 의 Regular, Medium, SemiBold, Bold 를 미리 다 로드해두면 편하다
- `await node.setTextStyleIdAsync(id)` 를 쓴다
- **스타일을 물리면 부분 범위 오버라이드가 초기화된다.** 검색어 하이라이트처럼 `setRangeFontName` 과 `setRangeFills` 로 넣은 것은 스타일 적용 뒤에 다시 넣는다
- 스케일에 없는 크기를 쓰고 싶으면 그 자체가 확인 항목이다. 임의로 만들지 말고 사용자에게 묻는다

### 좌표 기준값

**섹션 여백은 상하좌우 모두 200이다.** 콘텐츠를 다 배치한 뒤 마지막에 정규화한다.

| 요소 | 값 | 근거 |
|---|---|---|
| 섹션 여백 | **200** (상하좌우 동일) | 사용자 확정 |
| 대주제 라벨 | x = 200, 폭 375 (`template` 컴포넌트) | 컴포넌트 고정 폭 |
| **라벨 우측 간격** | **200** | 섹션 여백과 같은 리듬 |
| 콘텐츠 시작 x | **775** (200 + 375 + 200) | |
| 프레임 피치 | 560 (프레임 375 + 여백 185) | |
| 그룹 바 y | 행 기준선 | |
| 바 사이 간격 | **28** (케이스 바 y = 그룹 바 + 88) | 참고 파일 실측 |
| **바 → 프레임 간격** | **118** (프레임 y = 그룹 바 + 266) | 참고 파일 실측 중앙값 |
| 라벨 높이 | 그룹 바 top부터 프레임 bottom까지 = **1078** | |
| 행 사이 간격 | 200 (행 피치 **1278**) | 섹션 여백과 같은 리듬 |
| 프레임 | 375 × 812 | |
| 바 높이 | 60 | |

**세로 계산식** (행 기준선 `y0`):

```
그룹 바      y0
케이스 바    y0 + 88          (바 60 + 간격 28)
프레임       y0 + 266         (케이스 바 60 + 간격 118)
프레임 bottom y0 + 1078
다음 행      y0 + 1278        (행간 200)
```

**바와 프레임 간격을 118보다 좁히지 않는다.** Figma는 프레임 이름 라벨을 프레임 위쪽에 띄우는데, 간격이 좁으면 케이스 바에 가려서 안 보인다.

#### 피치는 주석 폭까지 계산해서 처음부터 잡는다 (디어 2026-09-22 확정)

```
피치 = 프레임 폭 + 40(간격) + 실제 쓸 주석 폭 + 130(여백)
```

| 프레임 | 주석 폭 | 피치 |
|---|---|---|
| 모바일 375 | 315 | 860 |
| 모바일 375 | 367 | 912, 넉넉히 **920** |
| PC 1600 | 367 | 2137, 넉넉히 **2140** |

위의 560은 **주석을 안 붙일 때만** 쓴다. 주석을 붙일 계획이면 처음부터 위 값으로 놓는다.

2026-09-22에 PC 프레임을 1785 피치로 놓고 나중에 주석을 붙이려다, 프레임 셋과 그룹 바와 케이스 바 다섯을 **전부 다시 옮겼다.** 주석 y는 요소 기준으로 다시 계산해야 해서 리더 라인까지 따라 움직였다.

### 상위 묶음 밴드 (선택)

스펙 문서가 행보다 큰 단위(Epic, 파트, 담당 조직)로 나뉘어 있으면 **대주제 라벨 왼쪽에 세로 밴드**를 하나 더 세운다. 여러 행을 세로로 관통해서, 스크롤 중에도 지금 어느 묶음인지 보인다.

| 요소 | 값 |
|---|---|
| 밴드 x | 200 (섹션 여백 자리) |
| 밴드 폭 | 120 |
| 밴드 우측 간격 | 80 → **라벨 x = 400, 콘텐츠 x = 975** |
| 밴드 높이 | 첫 행 y부터 마지막 행 bottom까지 = `(행수-1) × 1278 + 1078` |
| 텍스트 | -90° 회전, **상단 정렬**, SemiBold 36, 흰색 |

```js
// -90° 회전 후 밴드 상단 기준 정렬 (PAD = 56, W = 120)
t.relativeTransform = [[0, 1, W / 2 - t.height / 2], [-1, 0, PAD + t.width]];
```

**가운데 정렬하지 않는다.** 밴드가 5000 가까이 길어지면 가운데 텍스트는 밴드 시작점에서 안 보인다. 스크롤해 내려오다 밴드에 닿는 순간 읽혀야 한다.

**밴드 색은 바 팔레트와 겹치지 않게 채도를 낮춘 계열로 잡는다.** 바가 주인공이고 밴드는 배경이다. stroke는 없고 radius 8. 기존 과업 실측값을 그대로 쓴다.

| 밴드 | fill |
|---|---|
| 공통 | `#6E7881` |
| 묶음 1 | `#2E3A8C` |
| 묶음 2 | `#1F6FB2` |
| 묶음 3 | `#1E7A55` |

밴드 텍스트 형식은 `{묶음명}, {부제}` (예: `Epic 1, 선물 보내기`). 가운뎃점은 쓰지 않는다. 부제가 없으면 묶음명만 쓴다. **새 색을 지어내지 않는다.** 묶음이 4개를 넘으면 사용자에게 물어본다.

**밴드는 행이 묶음 안에 온전히 들어가야 그릴 수 있다.** 한 행에 두 묶음이 섞여 있거나 묶음 순서와 행 순서가 어긋나면 밴드가 끊긴다. 밴드를 세우기 전에 **행 이동과 순서 교체를 먼저 끝낸다.**

기존 골격에 밴드를 나중에 추가할 때는 **전체를 x += 200 밀고 나서** 밴드를 x=200에 만든다. 그 다음 여백 정규화.

### 여백 정규화 (마지막에 반드시 실행)

배치가 끝나면 이 스크립트로 여백을 맞추고 섹션 크기를 다시 잡는다. 좌표를 손으로 계산하지 않는다.

```js
const sec = await figma.getNodeByIdAsync("SECTION_ID");
const PAD = 200;
const kids = sec.children;
let minX = Infinity, minY = Infinity;
for (const c of kids) { minX = Math.min(minX, c.x); minY = Math.min(minY, c.y); }
const dx = PAD - minX, dy = PAD - minY;
for (const c of kids) { c.x += dx; c.y += dy; }
let maxX = -Infinity, maxY = -Infinity;
for (const c of kids) { maxX = Math.max(maxX, c.x + c.width); maxY = Math.max(maxY, c.y + c.height); }
sec.resizeWithoutConstraints(Math.round(maxX + PAD), Math.round(maxY + PAD));
return { mutatedNodeIds: kids.map(c => c.id), section: { w: Math.round(maxX + PAD), h: Math.round(maxY + PAD) } };
```

행을 추가할 때마다 다시 돌리면 된다.

### 바 스타일

**위계는 색이 아니라 불투명도로 만든다.** 그룹 바만 불투명하고 케이스 바는 전부 24%다. 색만 보고 100%로 칠하면 화면이 무거워지고 참고 파일과 다르게 보인다.

**stroke가 항상 있다.** 1px, INSIDE, radius 8. 반투명 바는 fill과 **같은 색 100%**, 불투명한 그룹 바만 **검정 20%**다.

| 역할 | variant | fill | fill 불투명도 | stroke |
|---|---|---|---|---|
| 그룹 바 | Primary | `#4D49FC` | **100%** | **검정 20%** |
| 케이스 바 (기본) | Primary | `#4D49FC` | **24%** | 같은 색 100% |
| 케이스 바 (중립) | Primary | `#828C94` | **24%** | 같은 색 100% |
| 조건 충족 | Primary | `#0079FA` | **24%** | 같은 색 100% |
| 최대 조건 충족 | Primary | `#15B869` | **24%** | 같은 색 100% |
| AS-IS 바 | Default | `#000000` | **40%** | 같은 색 100% |

텍스트는 전부 흰색, Pretendard SemiBold 18. 바 내부 패딩 18/24.

**clone은 원본의 fill과 stroke를 그대로 물려받는다.** 역할이 다른 바를 만들 때 fill만 덮어쓰면 stroke가 원본 값으로 남는다. **fill, stroke, strokeWeight, strokeAlign, cornerRadius를 매번 명시적으로 다 세팅한다.**

```js
const S = (c, o) => [{ type: "SOLID", color: c, opacity: o }];
const group = (c) => ({ fills: S(c, 1),    strokes: S(black, 0.2) });
const chip  = (c) => ({ fills: S(c, 0.24), strokes: S(c, 1) });
const asis  =       ({ fills: S(black, 0.4), strokes: S(black, 1) });
// 적용 후 n.strokeWeight = 1; n.strokeAlign = "INSIDE"; n.cornerRadius = 8;
```

### 바 텍스트 형식

| 종류 | 형식 | 예 |
|---|---|---|
| Primary (그룹) | `#{스펙번호} {대주제}` | `#1.1 PDP 진입점, CTA 영역` |
| Primary (케이스) | 프레임명만 | `1.1_PDP_기본` |
| Default (AS-IS) | 프레임명만 (언더바) | `AS-IS_주문완료` |

**그룹 바만 샵(`#`)으로 시작하고 부제에 가운뎃점을 쓴다.** 과업명 접두는 붙이지 않는다. 케이스 바와 AS-IS 바는 프레임명과 **글자 하나까지 같게** 유지하고 긴 설명을 넣지 않는다.

#### 이름은 스펙 문서에서 가져온다

프레임명을 짓기 전에 **스펙 문서의 해당 항목 제목을 먼저 읽는다.** 요약하거나 줄이지 말고 그 말을 쓴다.

| 층위 | 출처 | 지어내도 되나 |
|---|---|---|
| 스펙 번호 | 스펙 문서 그대로 | 절대 안 됨 |
| 화면명 | 스펙 항목 제목 | 안 됨 |
| 상태명 | 스펙에 대개 없음 | 만들되 아래 규칙 |

**스펙 번호는 재편된다.** 항목이 쪼개지거나 신설되면 뒷번호가 통째로 밀린다. 골격을 만든 뒤 원본이 갱신되면 **번호부터 대조한다.** 이름만 보면 안 틀린 것처럼 보인다.

대조 결과 스펙 문서 쪽 참조가 틀렸으면 고치지 말고 **작성자에게 알린다.** 스펙 문서가 SSOT다.

#### 상태 이름은 조어를 쓰지 않는다

프레임명의 `{상태}` 자리에 시스템어나 법률어를 넣으면 읽는 사람이 멈춘다. **화면에서 실제로 일어나는 일**로 쓴다.

| 쓰지 않는다 | 대신 |
|---|---|
| `체류중도과` (분석어 + 법률어) | `입력중만료` |
| `체류중변동` | `작성중변동` |
| `모듈해제` (시스템어) | `모듈전환` |
| `병존` (조어) | 결정 문구를 그대로. 예: `패키지담기유지` |

**결정 문서에 문장이 있으면 그 표현을 가져온다.** 프레임명으로 결정을 검색할 수 있어야 추적이 된다.

### 프레임 네이밍

기존 과업에서 확정한 언더바 규칙을 따른다. 자세한 건 `~/.claude/memory/work/feedback/feedback_wireframe-style.md`.

2.5_배송지_A             택1 비교안은 접미 _A _B _C
2.10_만료화면_TBD        미결은 접미 _TBD

**스펙보드 프레임(`00_스펙보드`)은 만들지 않는다** (디어 2026-09-29). 쓰지 않고 지우게 된다. 공통 스펙은 화면 옆 주석과 케이스 표로 전달한다.

## 함정

`use_figma` 호출 전에 반드시 `figma-use` 스킬을 로드한다. 그 외 이 작업에서 실제로 밟은 것들:

- **`layoutSizingHorizontal = "FILL"`은 부모가 auto-layout일 때만 된다.** 부모를 먼저 auto-layout으로 만들고 `appendChild` 뒤에 설정한다. 화면을 채우거나 폭을 바꿀 때 자주 쓴다. 참고 화면이 393 폭이면 루트만 375로 줄이지 말고 auto-layout 자식을 FILL로 물린 뒤 남은 393 노드를 전부 내려가며 375로 맞춘다
- **`use_figma`는 원자적이다.** 실패하면 아무것도 생성되지 않는다. 에러를 읽고 고친 뒤 다시 보낸다. 중복 생성 걱정은 없다
- **`figma.currentPage`는 호출마다 첫 페이지로 초기화된다.** 매 호출 시작에 `await figma.setCurrentPageAsync(page)`
- **텍스트를 건드리기 전에 그 노드의 현재 폰트를 로드한다.** `await figma.loadFontAsync(t.fontName)`. 하드코딩한 기본 폰트로 로드하면 실패한다
- **`get_metadata`는 큰 섹션에서 응답이 잘린다.** 노드가 많으면 `use_figma` 읽기 스크립트로 필요한 필드만 뽑는다
- **`importComponentByKeyAsync`는 키가 맞아도 실패할 수 있다.** 참고 파일에서 뽑은 키가 대상 파일에서 안 잡히면 퍼블리시나 권한 문제다. 위 `컴포넌트를 못 가져올 때` 순서를 따른다
- **라벨 폭을 빼먹고 콘텐츠를 배치하면 겹친다.** `template`은 375 폭이다. 콘텐츠 시작 x를 775로 잡거나, 배치 후 여백 정규화로 밀어낸다
- **`setProperties`로 variant를 바꾸면 텍스트 오버라이드가 날아간다.** variant마다 텍스트 레이어 이름이 달라서 오버라이드가 매칭되지 않는다. **순서를 지킨다: variant 먼저, 텍스트 나중.** 이미 텍스트를 넣은 인스턴스의 variant를 바꿨다면 텍스트를 다시 넣어야 한다
- **fill을 덮어쓸 때 텍스트 색도 같이 확인한다.** 검정 fill에 어두운 기본 텍스트가 얹히면 안 보인다. 바 텍스트는 흰색으로 통일한다
- **인스턴스 안에 중첩된 인스턴스의 variant를 바꾸면 부모 인스턴스가 통째로 그 자식으로 교체된다.** 2026-09-21 재현. 라이브러리 컴포넌트(ODS Date Picker) 안의 날짜 셀에 `Disabled=true`를 넣었더니 375x812 인스턴스가 54x40 날짜 셀로 바뀌었다. 노드 id는 그대로 남아서 알아채기도 늦다. **중첩 인스턴스의 상태는 API로 건드리지 않는다.** 필요하면 ① 사용자가 Figma UI에서 직접 찍거나 ② 단계별로 `detachInstance()` 해서 평범한 프레임 안으로 내린 뒤 건드린다. 디테치하면 라이브러리 링크가 끊기므로 사용자에게 먼저 알린다
- **텍스트 오버라이드는 중첩이어도 안전하다.** 깨지는 것은 variant 변경이다. 버튼 라벨 교체 같은 작업은 그대로 해도 된다
- **다른 페이지 원본을 쓸 때는 순서가 정해져 있다.** `setCurrentPageAsync` 나 `importComponentSetByKeyAsync` 를 먼저 부르면 그 뒤의 `getNodeByIdAsync` 가 다른 페이지 노드에 대해 `null` 을 돌려준다. 원자적이라 스크립트가 통째로 롤백된다. **① 전 페이지 `loadAsync` → ② 필요한 원본을 전부 변수로 확보 → ③ `setCurrentPageAsync` → ④ 생성과 임포트** 순서로 짠다. 2026-09-22에 이 순서를 틀려 같은 스크립트가 두 번 롤백됐다
- **예전 핸드오프에 적힌 노드 ID는 쓰기 직전에 다시 조회한다.** 과업이 정리되면서 프레임이 사라져도 문서에는 남는다. 2026-09-22에 02 페이지 `721:5xxxx` 대역이 통째로 없어졌고 같은 화면이 `745:19xxx` 로 남아 있었다. **ID가 아니라 이름으로 찾는 스크립트를 먼저 돌린다**
- **클론한 노드에서 앵커 문자열을 찾을 때 따옴표를 가정하지 않는다.** `insertCharacters` 앵커로 `"..."` 가 들어간 문장을 썼다가 못 찾았다. 곧은 따옴표와 둥근 따옴표가 섞여 있다. 따옴표를 뺀 조각으로 `indexOf` 한다

## 연계

- **`lofi-wire`** : HTML 와이어를 먼저 만들고 그 구조를 Figma로 옮길 때 이 스킬로 넘어온다
- **`spec-policy-handoff`** : 프레임 골격이 서고 화면을 채운 뒤 주석 단계에서 사용
- 프레임 목록과 네이밍의 출처는 과업 프로젝트 폴더 (`~/agent-workspace/projects/<slug>/references.md`)
